never signed in, with no snapshot ever adopted (`UpdateFailedToLoad` in logcat), lists

**D-09 - PASS at +2.96%**, not the +9.92% first reported. See below.

## D-09 re-measured, and why the first number was wrong

The original comparison put a build measured 2026-09-22 against one measured 2026-09-23.
Re-run back to back in one session, same offline state, both landing on the onboarding
screen:

| Build | median | mean | sd | min/max |
|---|---|---|---|---|
| baseline `b85fa55` (exam-less) | 557ms | 558.1 | 5.5 | 549/567 |
| exam-bearing `5518117` | 573.5ms | 574.8 | 6.1 | 567/585 |

**+16.5ms, +2.96%** (Welch t = 5.72 - small but real). The same baseline build measured
**557ms today vs 524ms yesterday: +33ms of pure session drift**, which was most of the
original 9.92%. Breakdown: ~4.7ms before `Start proc` (APK 127.4 -> 135.0 MB), +2.5ms in
bundle load/eval, +9.2ms in first render.

`TotalTime` was assumed to cover only the native splash. It does not - `Displayed` fires
after `Running "main"` - so JS evaluation and first render are inside it. The metric is
sound, but it is dominated by *which screen the app lands on*: an onboarded install
landing on home measured 1345ms, more than double. Any future before/after must hold
account state constant.

## Method faults found (each produced a confident wrong reading)

1. **Airplane mode did not isolate the device.** `airplane_mode_on=1` while Wi-Fi stayed
   associated and `ping` returned 0% loss. Cause: Android persists a "keep Wi-Fi on in
   airplane mode" preference. After an explicit `svc wifi disable` cleared it, airplane
   mode alone worked correctly and was used for the whole re-run. Paul was right that
   airplane mode works; the durable rule is that **the flag is not evidence** - confirm
   with `ping`. Had the app launched in the false state it would have pulled the v73
   snapshot and the seed-only proof would have measured the snapshot path.
2. **A bare `ealch://exam` always reads "No exams available yet."** `exam.tsx` needs a
   `format` param; without one the list is hardcoded empty. Demonstrated both ways on one
   running instance. Plan 06 recorded that string as proof of "0 exam papers" - true then,
   but not established by that evidence, and it would have read as total failure here.
3. **A dozing screen voids `am start -W`.** No `TotalTime` at all, `LaunchState: UNKNOWN`,
   and pure-black screenshots that look like a broken app.
4. **`grep` treats the JS bundle as binary**, so `grep -c` reports `1` regardless of
   content - which is exactly the threshold the plan's own APK check used (`>= 1`).

Items 1, 2 and 4 all affected checks that had already been written down as passing.
