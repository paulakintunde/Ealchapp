# Phase 22.1: Bundle exam content in the seed - Context

**Gathered:** 2026-09-22
**Status:** Ready for planning

<domain>
## Phase Boundary

Published exam papers and the tasks they reference ship inside `ealch-v2/src/content/seed.json`, generated by `content:publish` from the published database state, so a fresh or offline install lists every paper at first launch without waiting for the OTA snapshot. The snapshot keeps superseding bundled exams by id.

This reverses exam-pack decision 11.6 ("exams do not ship offline") for exam **text only**. Exam audio stays in Storage and resolves by `audioRef`. Grading still needs the network. Bundling makes papers visible and openable offline; it does not make them gradable offline, and this phase does not try to.

Not in scope: offline audio, offline grading, any new offline UX, a withdrawal/tombstone mechanism, a seed byte ceiling in publish.

</domain>

<decisions>
## Implementation Decisions

### What ships
- **D-01:** Every paper with `status = 'published'` at publish time ships in the seed (15 papers today). One rule, no subset list, no new `SEED_CUT` lever.
- **D-02:** Only exam tasks referenced by a bundled paper's sections ship, mirroring `cutItems` keeping only items a lesson references. Orphan published tasks (e.g. the 15 PE remediation tasks with no paper) stay OTA-only.
- **D-03:** A bundled paper naming a task id the seed does not carry refuses the publish. `validateCorpus` already checks exam referential integrity (`schema.ts` ~L4990), so putting `examPapers`/`examTasks` on the `seed` object in publish step 5 should make the existing `validateCorpus(seed)` refusal cover it. The researcher confirms the check actually fires on a dangling paper→task reference and adds it if not.

### Withdrawal and versioning
- **D-04:** Accept that a paper bundled in a binary and later unpublished stays on that install until the next app build. This is how lessons already behave (`mergeCorpus` overlays by id and never removes). A correction republished under the same id DOES reach devices through the overlay, which is criterion 2. No tombstones, no "snapshot is authoritative for exams" special case.
- **D-05:** A sitting in progress finishes on the paper/task versions it started on. A newer snapshot adopted mid-sitting applies to the next sitting only. **Today this is not true:** `exam-section.tsx` `useMemo`s `tasks` on `[section, corpus]`, and `refreshFromRemote` upgrades the live corpus in-session, so a mid-sitting swap would change the tasks under the candidate. The researcher sizes the change (e.g. pinning resolved tasks/paper into the sitting or draft at start) and flags it if it is larger than a small change; it must not conflict with Phase 23's restore/draft work.

### Offline behaviour (criterion 5)
- **D-06:** Record only. The phase measures and writes down exactly what a fresh offline install does with a bundled paper: the Examiner list, the paper screen, a listening section (audio from Storage) and a writing/speaking section (grading). Any trap it finds (stuck spinner, section that cannot be left, misleading status) becomes a follow-up phase, not a fix here.
- **D-07:** The device pass is literally a fresh install with airplane mode ON before first launch (uninstall, install the preview/release build, launch offline). Claude drives over adb; Paul does anything that needs hands.
- **D-08:** Criterion 1's "lists and opens" is proven in two steps, because entitlement cannot be obtained offline:
  - **(a)** Fresh install, airplane mode: the Examiner lists all published papers and each paper screen renders its sections, with the `examiner` gate where it normally sits.
  - **(b)** Grant entitlement online once, then airplane mode, force-close, reopen: every paper opens and a section starts. Note that going online in (b) also lets the snapshot download, so (b) proves offline opening, not seed-only content; (a) is the seed-only proof. Record the content version from `ealch://downloads` at each step so the report states which layer supplied the papers.

### Size and cold start (criterion 4)
- **D-09:** Record seed bytes before and after (baseline ~15.1 MB, exam text ~1.4 MB) and cold start on the Pixel 6, using the same method both times. If cold start regresses by more than about 10%, stop and bring the numbers to Paul before shipping (Phase 16's lazy load has not landed). Below that line, record and ship. No `MAX_SEED_BYTES` refusal in publish.

### Reversing decision 11.6 (criterion 3)
- **D-10:** Written down in code and in this CONTEXT, not in a separate doc. Rewrite the ExamTask/ExamPaper rationale block in `publish-content.ts` (~L215-227) and the "Why exam content is NOT in the guard above" comment (~L748-757) to say exams now ship in the seed, why, and cite phase 22.1. `EXAM-PACK-REDESIGN.md` is not amended.
- **D-11:** Keep `ealch-admin/scripts/exam/report-reachable.test.ts` in admin, because it checks ALL published papers against Postgres, which the seed cannot. Add a small `ealch-v2` test that every seed paper resolves all its task ids and that its format has a reporting instrument (`instrumentFor`). Also add the "seed carries exam papers" expectation next to `catalogue-ships.test.ts`'s style, so a publish that silently drops exams from the seed goes red.
- **D-12:** Extend the `no-silent-regression` publish guard to exam papers and tasks. A publish that would drop or downgrade a paper/task the committed seed carries must now refuse visibly, the same as lessons/units.
- **D-13:** Find and update every "exams are never in the seed" assumption deliberately (tests asserting absence, seed-cut scripts, comments, `drift-guard.logic.ts`, `publish-columns.test.ts`, `a2-29-hotel.test.ts`, `schema.test.ts` if they encode absence). None may be left silently contradicting the new seed.

### Producing the first exam-bearing seed
- **D-14:** The exam cut lives in `content:publish` (durable: every future publish carries exams). The phase's real publish runs only after `pnpm content:parity` and `scripts/_publish_blockers.ts` report nothing seed-ahead. The current working tree has an uncommitted `seed.json` and the sons+a1 narration batch's DB reconciliation is pending, so that work must be reconciled into Postgres first (per the seed-direct hazard). The phase cannot close until that publish is clean. Follow the standing rule: dry run in the same session, and run the full suite against the freshly regenerated seed before calling it done.

### Phase 23 follow-through
- **D-15:** When 22.1 lands, amend `.planning/phases/23-exam-recording-task-restore-grading-path-integrity/23-CONTEXT.md` D-14: the dev-build pass uses the bundled papers and needs no temporary patch lifting the `__DEV__` guards. The EAS preview pass is unchanged. The guards themselves stay.

### Claude's Discretion
- How the exam cut is expressed in code (inline in publish step 5 vs a helper in `seed-cut.logic.ts` next to `cutItems`); prefer the helper so `check-seed-db-parity` can share the rule, as `cutItems` does.
- Cold-start measurement method (e.g. `adb shell am start -W` TotalTime over N runs), provided before and after use the same method and device.
- Exact wording of the rewritten publish comments.

<code_context>
## Existing Code Insights

### Reusable Assets
- `mergeCorpus` already overlays `examTasks`/`examPapers` by id, so criterion 2 needs no new merge code, only a test proving a snapshot paper replaces the seed paper.
- `validateCorpus(seed)` in publish already refuses an incoherent seed and covers exam references (D-03).
- `cutItems` in `seed-cut.logic.ts` is the model for a referenced-only exam task cut shared with the parity check.
- The publish exam read already produces `examTasks`/`examPapers` with provenance withheld; the seed can reuse those arrays filtered.

### Established Patterns
- The seed must be a valid corpus on its own; publish exits before writing anything if not.
- The seed is regenerated from Postgres, never hand-merged, and tests must survive regeneration (deep compare, not `JSON.stringify` equality).
- The catalogue ships whole; exams ship as published papers plus referenced tasks.

### Integration Points
- `home.tsx` Examiner card counts and `exam.tsx` paper list read the merged corpus, so bundled papers appear with no screen changes. Verify that on the device.
- A dev build (seed only, no cache overlay) will now show bundled exams, which changes Phase 23's dev-pass setup (D-15) and the memory that dev builds cannot show exams.
- `MAX_SNAPSHOT_BYTES` (30 MiB) is unaffected: exams were already in the snapshot.

</code_context>

<specifics>
## Specific Ideas

- "Same as lessons" is the governing analogy for withdrawal and merge behaviour. Exams must not grow a special merge rule.
- The offline device pass must say which content layer (seed or snapshot) supplied the papers at each step, read from `ealch://downloads`.

</specifics>
