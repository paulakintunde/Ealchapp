# Phase 22.1: Code Review Report

**Reviewed:** 2026-09-25
**Depth:** deep
**Files Reviewed:** 19
**Status:** issues_found

## Summary

Reviewed the exam-seed-cut, no-silent-regression guard, sitting pin, and merge/parity
work for phase 22.1 against the six focus questions in the review brief. The core logic
is sound and well tested: `cutExamTasks`/`paperTaskIdSet`/`examCutDrift` correctly
implement D-01/D-02 (papers unfiltered, tasks referenced-only) with real, non-tautological
unit tests; `findExamPaperLosses`/`findExamTaskLosses` correctly wire into
`publish-content.ts`'s existing no-silent-regression block against the FULL published set
(not the seed cut), matching the doc comments; the exam-task `targetItemIds` union into
`seedItems` is deduped and backstopped by `validateCorpus(seed)`, which fails the publish
outright if the union is ever wrong (verified: this is exactly how the 2,137-dangling-ref
bug was caught during plan 04); `pinSitting`/`pinnedTasksOf` correctly implement the D-05
monotonic freeze (verified against real behavioral tests, not source-grep); and the
`mergeCorpus` snapshot-supersedes-seed test in `content.logic.test.ts` calls the real
function and asserts real behavior. No O(n²) blowups were found in any of the new code
over the ~49k-item corpus — every new pass is a linear scan against a `Set`/`Map`.

Four issues are worth surfacing before this ships further, none of which are proven data-
loss or crash bugs, but which affect exam-content protection, the guard's own escape-valve
completeness, and one React anti-pattern:

## Warnings

### WR-01: Bundling exam content into the binary makes every published paper's answer key, rubric, model answer and internal examiner notes trivially extractable from the APK with zero account, network, or app execution

**File:** `ealch-admin/scripts/publish-content.ts:408-440`, `:1076-1146`
**Issue:** Before this phase, `examPapers`/`examTasks` shipped only through the OTA
snapshot, which required the app to run online at least once before any exam content
existed on a device (confirmed by the phase's own baseline: `unzip -p <apk>
assets/index.android.bundle | grep -c "paper.tef_canada.blanc-01"` → `0` on the pre-phase
APK, per `22.1-VALIDATION.md`'s Plan 06 measurements). After this phase, the same
`unzip`+`grep` against the exam-bearing APK returns all 15 papers — this is literally the
verification technique the phase itself used to prove the feature works
(`22.1-VALIDATION.md` lines 193-203). That command needs no device, no account, and no
network: anyone who can download the APK (Play Store, an APK mirror, a leaked build) can
extract, in cleartext:
  - every closed task's QCM `correct` answer index (`schema.ts` `items[].correct`),
  - every open task's `rubric` and `modelAnswer` (`publish-content.ts:424-425`),
  - `examinerNotes` (`publish-content.ts:426`) — a field with no doc comment, never read
    or rendered by any app screen (confirmed by a repo-wide grep), i.e. internal-only
    content that is nonetheless now shipped to every device and extractable from the
    binary.

  The exam-tier gate (`examGateOn`, `exam-paper.tsx`'s `go()`) is a client-side UI check
  only — it decides whether the *screen* opens, not whether the *content* exists on the
  device. `examGateOn` ships `false` today (per `22.1-VALIDATION.md`'s own follow-up #2),
  so there is no live paywall to bypass yet, and the exam papers are the team's own
  authored mock content rather than licensed real exams, which lowers the immediate
  stakes. But the moment `examGateOn` is switched on for real monetization ("Exam papers
  are a separate pass" — the paywall copy quoted in `22.1-VALIDATION.md`'s T-22.1-21
  section), the pass is enforced by nothing beyond the padlock icon: the underlying
  answer keys for every locked paper are already sitting in plaintext in the binary every
  installed copy of the app carries.

  None of D-01 through D-15 in `22.1-CONTEXT.md` evaluate this trade-off — the phase's own
  decision record only discusses *whether* exam text should ship offline (reversing
  11.6), never *how easily extractable* shipping it in the binary (vs. a runtime-fetched,
  account-gated snapshot) makes the paid tier's content.
**Fix:** Not a code fix so much as a decision that should be made explicitly before
`examGateOn` is ever flipped `true` in production — e.g., keep gated/higher-tier formats
OTA-only (reintroducing a narrower version of 11.6 for paid formats specifically), fetch
gated exam content server-side at attempt time instead of shipping it client-side at all,
or accept the exposure in writing as a documented risk. At minimum, drop `examinerNotes`
from the seed cut (and from the snapshot) if it is genuinely never meant to reach a
candidate's device — it currently isn't filtered by anything.

### WR-02: The no-silent-regression guard has no escape valve for a legitimate downsizing edit to exam content, unlike every other content kind it protects

**File:** `ealch-admin/scripts/drift-guard.logic.ts:47-100` (contrast), `:194-241`
(`findExamPaperLosses`)
**Issue:** `findVersionedLosses` (lessons, scenarios, playlists, speak stages) only
enforces its richness-shrink check `if (db.version === git.version && signals)` (line 85)
— a DB with a *higher* version is explicitly allowed to trim ("a higher DB version is
allowed to trim", per the doc comment at line 50). That is the supported way an author
signals "I meant to remove this," and it is exactly how `restore-lesson-bodies-from-seed.ts`
and friends recover from an accidental regression versus an intentional edit.

  `ExamPaper`/`ExamTask` carry no version field (repeatedly noted in the phase's own
  comments and SUMMARY), so `findExamPaperLosses`/`findExamTaskLosses` have no equivalent
  signal to consult. Every shrink — a paper's task roster getting smaller, a task's
  `items`/`parts` count getting smaller, a rubric/model answer/interlocutor/debate bank
  disappearing — is *unconditionally* reported as a loss and blocks the publish, with no
  way to say "this one is deliberate." The guard's own remediation text
  (`publish-content.ts:745-750`, "re-apply with scripts/exam/apply-paper.ts... There is no
  override flag, the same as lessons") describes only the accidental-regression recovery
  path (push the old richer content back into Postgres) — it has nothing to say to an
  author who has *decided* to shorten a published paper's speaking épreuve or drop a bad
  question from a task, a normal editorial operation that lessons/scenarios/playlists
  handle today via a version bump.
**Fix:** Either give `ExamPaper`/`ExamTask` a version field so the existing
`findVersionedLosses` escape valve applies uniformly, or add an explicit, logged
allowlist/ack mechanism scoped to exam content (per the file's own stated policy at line
32: "If one is ever added, it must log the specific kind+id it overrides"). Until then,
a legitimate content trim to a published paper has no path through `content:publish`
short of manually forcing the shrunk content into Postgres and re-publishing — which is
the same operation the guard exists to make un-doable by accident, now required as the
only doable path on purpose.

### WR-03: `findExamPaperLosses` cannot see a same-count task swap inside a section, unlike the equivalent unit/lessonId comparator

**File:** `ealch-admin/scripts/drift-guard.logic.ts:194-241`; contrast
`findUnitLosses:109-146`; test at `drift-guard.logic.test.ts:297-305`
**Issue:** `findUnitLosses` tracks the unit's lesson roster *by id*
(`dropped = (git.lessonIds ?? []).filter((id) => !dbIds.has(id) && ...)`, line 132) — if a
committed lessonId is replaced by a different one at the same array length, it is still
caught, because the check is set-membership, not a length comparison.

  `findExamPaperLosses` only compares total task count per section
  (`dbTaskCount < gitTaskCount`, line 217) and the set of skills present (line 228-237). A
  publish that swaps `t2` out of a section for a different task `t99` at the same task
  count and same skill produces zero losses — the test at
  `drift-guard.logic.test.ts:297-305` confirms this is by design ("the same tasks in a
  different order is a routine edit, not a loss" — but the fixture used there is a pure
  reorder; nothing tests the actual swap-to-a-different-id case this comment implies is
  also covered). If `t2` happened to be quietly dropped from the paper without being
  unpublished elsewhere, it silently falls out of the next seed's `examTasks` cut (D-02,
  correctly, since it becomes unreferenced) with no guard signal at the paper level.
**Fix:** Low priority given `changedPapers` in `examCutDrift` already surfaces a
sections-diff informationally at parity-check time, but for guard parity with
`findUnitLosses`, consider comparing the specific `taskIds` sets per section (not just
counts) so an id-level swap is visible the same way a lessonId swap is.

### WR-04: The sitting pin mutates a ref inside a `useMemo` factory, a React anti-pattern that is currently safe only because `pinSitting` happens to be idempotent

**File:** `ealch-v2/app/exam-section.tsx:104-108`
**Issue:**
```ts
const pinRef = useRef<SittingPin | null>(null);
const sitting = useMemo(() => {
  pinRef.current = pinSitting(pinRef.current, section, tasks);
  return pinRef.current;
}, [section, tasks]);
```
React's documentation is explicit that a component "should not write or read
`ref.current` during rendering" except for lazy one-time initialization, because the
render function (and anything called from it, including a `useMemo` factory) is expected
to be pure — React may call it more than once for a commit it discards (Strict Mode's
double-invoke, offscreen/prerendering, or a future concurrent feature), and code that
mutates external state during render should not assume it only runs once per committed
render. This currently causes no observable bug only because `pinSitting(prev, section,
tasks)` is deterministic and idempotent for repeated calls with the same arguments — a
discarded, re-run render simply recomputes and reassigns the same value. That invariant
is not enforced anywhere and would silently stop holding if `pinSitting` ever gained any
non-idempotent behavior (e.g., a side-effecting log, a counter, a `Date.now()` freeze
timestamp for a future feature).
**Fix:** Move the ref write out of the render pass — e.g., compute the next pin value in
a plain (pure) expression inside `useMemo` without touching `pinRef.current`, and commit
it to the ref from a `useEffect` (or keep the current shape but explicitly document the
idempotency invariant `pinSitting` must never break, with a test enforcing it, since the
whole pattern's safety rests on that one property).

## Info

### IN-01: One new wiring test is source-grep only where a behavioral equivalent would catch more

**File:** `ealch-v2/src/store/examSection.logic.test.ts:750-774`
**Issue:** "the section runner reads its roster through the sitting pin (phase 22.1 D-05)"
asserts via string-matching on `exam-section.tsx`'s source (`pinnedTasks.map(`,
`pinnedTasks.reduce(`, `!src.includes('tasks.reduce(')`, etc.) rather than mounting the
component and exercising a mid-sitting corpus swap end to end. This matches the file's
existing established convention (most of its "wiring" tests are source scans, per its own
header comment), and the underlying pin logic itself is covered by real behavioral tests
in `examSitting.logic.test.ts`, so this is not a coverage gap in practice — but a
source-grep test can pass even if the *values* passed to `pinnedTasks.map`/`.reduce` were
subtly wrong (e.g., an unrelated variable also named `pinnedTasks` in a refactor), which a
rendered-component assertion would not miss.
**Fix:** No action required; noting for completeness per the review brief's explicit
"tautological/source-grep-only" focus question. If this screen ever gets a component-test
harness, a real mid-sitting-refresh integration test would be a strictly stronger
substitute for this one test.
