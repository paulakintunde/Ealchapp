**Researched:** 2026-09-22
**Domain:** Content publish pipeline (Postgres → seed.json → app corpus), exam-content referential integrity, offline-first bundling
**Confidence:** HIGH — every claim below is either read directly from the current repo (file:line) or measured live against the real Supabase project this session (`ogbothupjcivwruesgsu` mirror, `aws-0-ca-central-1.pooler.supabase.com`). ## Summary

This phase is a well-bounded, single-repo change with one real design decision (D-05's pinning) and a lot of careful bookkeeping (D-03, D-11, D-12, D-13). All nine of the CONTEXT.md's open research questions resolved with direct evidence; none needed a `[CITED]` external source, and only the D-05 sizing recommendation below counts as `[ASSUMED]` design judgment (a concrete but not-yet-implemented approach).

The mechanical part is small: `publish-content.ts` step 5 (~L1088-1092) currently builds the `seed: Corpus` object without `examTasks`/`examPapers` at all — they are read into `corpus` (the full, unbundled object) at step 1 but never carried into `seed`. Adding two lines plus a small `cutExamTasks` helper (mirroring `cutItems` in `seed-cut.logic.ts`) is the entire "ship exams in the seed" change. `validateCorpus` already refuses a dangling paper→task reference (schema.ts:5157-5175) — confirmed live, no schema change needed (D-03). `mergeCorpus` already overlays `examTasks`/`examPapers` by id (content.logic.ts:76-77) — criterion 2 needs only a test.

The two genuinely non-trivial pieces are:

1. **D-12 (no-silent-regression for exams):** `ExamPaper` and `ExamTask` carry **no `version` field** (schema.ts:2440-2547, 2592-2603), so the existing `findVersionedLosses` comparator (drift-guard.logic.ts:52) cannot be reused verbatim the way it is for lessons/scenarios/playlists/speak-stages. A new, structural (deletion + roster-shrink) comparator is needed, shaped like `findUnitLosses` (which also has no version field to key on) rather than `findVersionedLosses`.
2. **D-05 (pin a sitting's tasks):** `exam-section.tsx:95` memoises `tasks` on `[section, corpus]`, and `corpus` is a live zustand-subscribed value that `refreshFromRemote` mutates mid-session. The fix is genuinely small (one pinning ref, ~15-30 lines, confined to `exam-section.tsx` since exactly one binding named `tasks` is consumed by every downstream site — verified by grep). But it has a real interaction with two *other* things this session found: (a) Phase 23's BUG-05 hold-and-wait-at-submit logic, which needs the corpus to still resolve newly-appearing tasks that were missing at mount, and (b) an **existing regression test** (`examSection.logic.test.ts:683-735`) that will fail if the pin is implemented by removing `corpus` from the `tasks` `useMemo`'s dependency array. Both are addressed in Architecture Patterns / Common Pitfalls below with a concrete non-conflicting design.

**Primary recommendation:** Add `examPapers`/`examTasks` to the seed object in `publish-content.ts` step 5 via a new `cutExamTasks`/`cutExamPapers` pair in `seed-cut.logic.ts` (all published papers ship per D-01; tasks are cut to referenced-only per D-02); extend the no-silent-regression guard with a new `findExamLosses` structural comparator (no version field, so deletion + section/task-roster-shrink only); pin `exam-section.tsx`'s resolved tasks via an additive ref that never shrinks or replaces an already-resolved task, layered *underneath* the existing live `useMemo` (not replacing it) so the existing cold-start regression test keeps passing; and update the five confirmed "exams are never in the seed" comments/tests found below (D-13).

### Pattern 1: Referenced-only exam-task cut, mirroring `cutItems`
**What:** All published papers ship whole (D-01: no filtering — `content_exam_papers` is already queried `where status = 'published'` at step 1, so `corpus.examPapers` IS the seed set). Tasks are filtered to only those referenced by a bundled paper's sections (D-02), the same "referenced, not theme-wide" shape `cutItems` uses for items via `neededItemIds`.
**When to use:** Step 5 of `publish-content.ts`, alongside `seedItems = cutItems(...)`.
**Example (new code for `seed-cut.logic.ts`, following the file's existing style):**
```typescript
// Source: pattern mirrors cutItems (seed-cut.logic.ts:115-118), same file
import type { ExamPaper, ExamTask } from '../../ealch-v2/src/content/schema.ts';

/** Every exam task id a set of papers' sections point at. */
export function paperTaskIdSet(papers: Pick<ExamPaper, 'sections'>[]): Set<string> {
  return new Set(papers.flatMap((p) => (p.sections ?? []).flatMap((s) => s.taskIds ?? [])));
}

/** The exam task cut: only tasks a bundled paper actually references.
 *  Mirrors cutItems — publish-content.ts calls this; check-seed-db-parity.ts
 *  should call it too, so the build and the check cannot drift (D-14). */
export function cutExamTasks(tasks: ExamTask[], seedPapers: ExamPaper[]): ExamTask[] {
  const needed = paperTaskIdSet(seedPapers);
  return tasks.filter((t) => needed.has(t.id));
}
```
And in `publish-content.ts` step 5 (~L1088-1092), the `seed: Corpus` literal gains two lines:
```typescript
const seed: Corpus = {
  version, domains, themes,
  units: seedUnits, lessons: seedLessons, items: seedItems,
  scenarios: seedScenarios, playlists: seedPlaylists, speakPath: seedSpeak,
  examPapers,                              // D-01: every published paper, unfiltered
  examTasks: cutExamTasks(examTasks, examPapers), // D-02: referenced-only
};
```
`validateCorpus(seed)` at line 1097 then runs unchanged and already catches any dangling reference the cut might (in theory, cannot in practice since D-02 derives directly from `examPapers`) introduce.

### Pattern 2: Structural (non-versioned) drift-guard comparator for exams — D-12
**What:** `ExamPaper`/`ExamTask` have no `version` field (confirmed: schema.ts:2440-2547 for `ExamTask`, schema.ts:2592-2603 for `ExamPaper` — neither carries one). `findVersionedLosses` (drift-guard.logic.ts:52) requires `T extends { id: string; version: number }` and cannot type-check against either. The existing comparator with the right shape is `findUnitLosses` (drift-guard.logic.ts:109), which also has no version to key on and instead treats (a) disappearance and (b) roster shrinkage as the loss signal.
**When to use:** Add a new `findExamLosses` in `drift-guard.logic.ts`, called from `publish-content.ts`'s step 4·0 block (~L634-694) alongside the existing `findVersionedLosses`/`findUnitLosses` calls, using the SAME `committed` (git HEAD `seed.json`) vs `live` (this publish's DB read) shape.
**Recommended structure** `[ASSUMED — design not yet in the codebase, but derived directly from the two existing patterns above]`:
```typescript
// New in drift-guard.logic.ts, alongside findUnitLosses
import type { ExamPaper, ExamTask } from '../../ealch-v2/src/content/schema.ts';

export function findExamPaperLosses(args: {
  committed: ExamPaper[] | null | undefined;
  live: Map<string, ExamPaper>;
}): DriftLoss[] {
  const { committed, live } = args;
  if (!committed) return [];
  const losses: DriftLoss[] = [];
  for (const git of committed) {
    const db = live.get(git.id);
    const gitTaskCount = (git.sections ?? []).reduce((n, s) => n + (s.taskIds?.length ?? 0), 0);
    if (!db) {
      losses.push({ kind: 'exam paper', id: git.id,
        message: `${git.id}: in the committed seed (${gitTaskCount} tasks) but NOT published in the DB — this publish would DELETE it` });
      continue;
    }
    const dbTaskCount = (db.sections ?? []).reduce((n, s) => n + (s.taskIds?.length ?? 0), 0);
    if (dbTaskCount < gitTaskCount) {
      losses.push({ kind: 'exam paper', id: git.id,
        message: `${git.id}: the committed seed has ${gitTaskCount} tasks across its sections, the DB paper has only ${dbTaskCount} — this publish would SHRINK it` });
    }
    // Section count itself (four épreuves) is a stronger signal than task count alone —
    // a paper that drops a whole épreuve but keeps others' task counts up would hide here.
    const gitSections = new Set((git.sections ?? []).map((s) => s.skill));
    const dbSections = new Set((db.sections ?? []).map((s) => s.skill));
    const droppedSkills = [...gitSections].filter((s) => !dbSections.has(s));
    if (droppedSkills.length) {
      losses.push({ kind: 'exam paper', id: git.id,
        message: `${git.id}: the committed seed has a ${droppedSkills.join(', ')} épreuve the DB paper no longer has — this publish would DROP it` });
    }
  }
  return losses;
}

export function findExamTaskLosses(args: {
  committed: ExamTask[] | null | undefined;
  live: Map<string, ExamTask>;
}): DriftLoss[] {
  const { committed, live } = args;
  if (!committed) return [];
  const losses: DriftLoss[] = [];
  for (const git of committed) {
    const db = live.get(git.id);
    if (!db) {
      losses.push({ kind: 'exam task', id: git.id,
        message: `${git.id}: in the committed seed but NOT published in the DB — this publish would DELETE it` });
      continue;
    }
    // Presence-only, same spirit as findPresenceLosses: a rubric/modelAnswer/
    // interlocutor/debate bank vanishing without the task id vanishing is the
    // "downgrade" shape for a task (no version to detect a revert by).
    const fields: [string, (t: ExamTask) => boolean][] = [
      ['a rubric', (t) => !!t.rubric], ['a model answer', (t) => !!t.modelAnswer],
      ['an interlocutor bank', (t) => !!t.interlocutor], ['a debate bank', (t) => !!t.debate],
    ];
    for (const [label, present] of fields) {
      if (present(git) && !present(db)) {
        losses.push({ kind: 'exam task', id: git.id,
          message: `${git.id}: the committed seed has ${label} and the DB does not — this publish would ERASE it` });
      }
    }
  }
  return losses;
}
```
**Note for the planner:** this is a DESIGN RECOMMENDATION derived from the two existing patterns in the file, not code that exists today — mark it `[ASSUMED]` in the plan and treat the exact field list / message wording as Claude's discretion at implementation time, same as D-12 itself grants.

### Pattern 3: Pin a sitting's tasks without breaking the cold-start regression test — D-05
**What:** `exam-section.tsx:90-95` currently:
```typescript
const corpus = useContent((s) => s.corpus);
const paper = useMemo(() => (paperId ? content.examPaper(paperId) : null), [paperId, corpus]);
const section = useMemo(() => paper?.sections.find((s) => s.skill === skill) ?? null, [paper, skill]);
const tasks = useMemo(() => (section ? content.examTasksOfSection(section) : []), [section, corpus]);
```
`tasks` is consumed at exactly 6 further call sites in the file (verified by grep: L251, L253, L289, L413 deps array, L432, L438, L507) — a single binding, which is what keeps the fix small.

**The conflict this research found:** `ealch-v2/src/store/examSection.logic.test.ts:683-735` (`'every exam screen that reads the corpus re-reads it when it changes'`) statically parses every `useMemo` in `exam-section.tsx` (and the three other exam screens) whose body calls a `content.exam*`/`examTasksOfSection(` accessor, and FAILS if `corpus` is not in that `useMemo`'s dependency array. This test exists specifically because of a real, previously-shipped bug (cold-start "no exams available yet" that never cleared). If D-05 is implemented by simply deleting `corpus` from the `tasks` memo's deps (the naive pin), this exact regression test breaks — and for a good reason: the naive pin would reintroduce a real class of the bug it is protecting against (a task that legitimately has not resolved yet at mount would now never resolve, ever, for the life of the mounted screen).

**Recommended shape** `[ASSUMED — design derived from the constraint above, not existing code]`: keep the `tasks` `useMemo` exactly as it is today (satisfies the existing test, and correctly re-resolves tasks that were missing at mount — this is what Phase 23's D-08 hold-and-wait needs to observe). Add a SEPARATE ref that only ever grows/freezes, never shrinks or replaces an already-resolved task:
```typescript
// Additive pin: once a taskId first resolves, its content is frozen for the
// life of this mounted screen, even if a later refreshFromRemote() changes
// corpus.examTasks under it (D-05). Tasks that have NOT resolved yet keep
// coming from the live `tasks` memo above, so Phase 23's submit-time hold
// (BUG-05, exam-section.tsx submit()) still observes them resolving.
const pinnedTasksRef = useRef<Map<string, ExamTask>>(new Map());
for (const task of tasks) {
  if (!pinnedTasksRef.current.has(task.id)) pinnedTasksRef.current.set(task.id, task);
}
// Downstream code (submit(), answeredCount, totalCount, the render map) reads
// this instead of `tasks` directly:
const pinnedTasks = section
  ? (section.taskIds ?? []).map((id) => pinnedTasksRef.current.get(id)).filter((t): t is ExamTask => !!t)
  : [];
```
This satisfies D-05 (a task, once seen, never changes shape mid-sitting — a correction adopted mid-session cannot alter what the candidate is answering), keeps `examSection.logic.test.ts:683-735` green (the live `tasks` memo is untouched, `corpus` stays in its deps), and composes with Phase 23's D-08 (the hold-and-wait logic can keep polling `tasks`/`examTasksOfSection` for newly-resolved ids; once one appears, it gets pinned and never moves again). **Flag this explicitly for Phase 23's planner**: 22.1 lands first (per ROADMAP ordering), so Phase 23's submit()-time hold should read from the same pinning mechanism rather than inventing a second one.

### Anti-Patterns to Avoid
- **Do not replace the `tasks` useMemo's dependency array to exclude `corpus`.** This is the naive/obvious fix for D-05 and it is wrong twice: it breaks `examSection.logic.test.ts:683-735` (a real regression test for a real prior bug), and it starves Phase 23's BUG-05 hold-and-wait of ever seeing a late-resolving task.
- **Do not give `ExamTask`/`ExamPaper` a synthetic `version` field just to reuse `findVersionedLosses` unchanged.** Neither carries one today by design (they are DB rows re-read fresh every publish, never hand-edited in git the way lessons are — see the now-stale rationale at publish-content.ts:748-757 that D-10 asks to rewrite, not remove). Adding a version field is a bigger, schema-level change this phase does not need; the structural `findExamLosses` comparator (Pattern 2) is the narrower fix.
- **Do not add exam content to `SEED_CUT` in `seed-cut.config.ts`.** `SEED_CUT` governs the LESSON/ITEM/theme cut (tracks, units, themes, speakWorlds) — exams are a parallel, independent cut driven by D-01/D-02 (every published paper + its referenced tasks), not by track/theme membership. Mixing the two config shapes would misrepresent the actual rule.

## Common Pitfalls

### Pitfall 1: Confusing "committed seed" with "working-tree seed" when judging publish safety
**What goes wrong:** Running `pnpm content:parity` clean does not guarantee the actual `content:publish` run will pass its no-silent-regression guard, because the parity checker compares the WORKING-TREE `seed.json` to the DB, while the guard inside `publish-content.ts` compares the GIT-HEAD-COMMITTED `seed.json` to the DB (publish-content.ts:611-620).
**Why it happens:** Two different scripts, two different file sources, same variable name (`seed`/`committed`) in each — easy to conflate.
**How to avoid:** Before the real publish (D-14), the plan must include an explicit step to reconcile git HEAD and the working tree (commit the current `seed.json`, or discard it and re-derive), not just run `content:parity`.
**Warning signs:** A clean `content:parity` immediately followed by a `content:publish --dry-run` that still reports no-silent-regression losses.

### Pitfall 2: The naive D-05 fix breaks a real, working regression test
**What goes wrong:** Removing `corpus` from `exam-section.tsx`'s `tasks` `useMemo` dependency array (the obvious way to "stop re-reading the corpus mid-sitting") makes `examSection.logic.test.ts:683-735` fail, and reintroduces the exact class of bug that test was written to prevent (a task/paper that legitimately has not resolved yet at mount time would then never resolve for the life of the screen).
**Why it happens:** D-05's wording ("finishes on the paper/task versions it started on") and the cold-start bug's fix ("must re-read the corpus when it changes") sound contradictory but are not — the correct resolution is additive pinning (Pattern 3), not removing the live dependency.
**How to avoid:** Implement the pin as a separate, monotonically-growing ref layered under the existing live memo, per Pattern 3. Do not touch the `tasks` memo's own dependency array.
**Warning signs:** `examSection.logic.test.ts` (or any of the four exam screens' cold-start dependency tests) goes red during implementation.

### Pitfall 3: Treating `ExamTask`/`ExamPaper`'s lack of a `version` field as an oversight to fix
**What goes wrong:** Adding a `version: number` field to make D-12's guard reuse `findVersionedLosses` unchanged is a bigger, schema-level, cross-cutting change (touches `schema.ts` types, `validateExamTask`/`validateExamPaper`, the publish mapping, every existing exam test fixture in `schema.test.ts` and the 15 authored papers in `ealch-admin/scripts/exam/*`) — far larger than this phase's stated scope.
**Why it happens:** It looks like the "consistent" fix once you see lessons/scenarios/playlists/speak-stages all have one.
**How to avoid:** Use the structural comparator (Pattern 2), which needs no schema change — exactly the same reasoning `findUnitLosses` already uses for `Unit`, which also has no `version` field (drift-guard.logic.ts:103-105, explicit comment: "Units have NO version field... so the only loss-shaped signal is the lesson roster").
**Warning signs:** A plan task that touches `schema.ts`'s `ExamTask`/`ExamPaper` type definitions is a strong signal the scope has crept past D-12's actual ask.

### Pitfall 4: Assuming `SEED_CUT` (seed-cut.config.ts) is where the exam cut rule belongs
**What goes wrong:** `SEED_CUT` is a curated, human-reviewable "what ships offline for a brand-new learner" config keyed on tracks/units/themes/speakWorlds — none of which apply to exams (D-01/D-02's rule is "every published paper, referenced tasks only," with no curation knob).
**Why it happens:** It is the file CONTEXT.md's canonical refs mention alongside `seed-cut.logic.ts`, so it is tempting to add an `exams` field to it "for consistency."
**How to avoid:** Only `seed-cut.logic.ts` (the LOGIC file) needs new exports (`cutExamTasks`); `seed-cut.config.ts` (the CONFIG file) needs no changes, since D-01/D-02 leaves nothing to configure.
