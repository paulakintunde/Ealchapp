**The blocker, and why the tool's remedy was wrong here.** The dry run refused
with `a2.20.l1: DB is v3, committed seed is v4 — this publish would REVERT it`.
Three-way state was Postgres v3, working tree v3, committed HEAD v4: the working
tree already agreed with the database and git held the stale value. The guard
reads the committed seed, so it saw git as ahead.

Its suggested remedy, `restore-lesson-bodies-from-seed.ts`, pushes the committed
body *into* Postgres. That v4 was an accidental version bump Paul had deliberately
reverted, and `Lesson.version` keys learner progress. Following the tool would
have put v4 in the DB, the publish would have written v4 into the seed, and a2.20
progress would have reset. The fix was the opposite direction: commit the working
tree (f32f05d). a2.20.l1 came back from the regeneration as v3, as predicted.

Worth recording for later phases: `attempts`, `learning_sessions`, `entitlements`
and `subscriptions` are all **0 rows**. The version constraint that shaped this
was protecting nothing yet.

## The a1.03 fallout, and two tooling bugs

Bundling exams moved 23 of a1.03's printed ending figures and turned 4 tests red.
Re-measured per `_a1_genre_remeasure.ts`'s own rule ("always re-measure, never
restore the row"). Two real bugs surfaced:

1. The rewriter knew only the multi-line row format (`items: 58,`) and not the
   single-line one (`items: 46 }`). 14 of 27 rows were unreachable; a remeasure
   died on `-in` and wrote nothing.
2. `genre-endings.ts` is CRLF, and appending after `split('\n')` put text beyond
   a carriage return, which ECMAScript treats as a line terminator — the `//`
   comment ended there and the rest became code.

Both fixed, reasons recorded in place, rewriter now idempotent.

**Known and deliberately not fixed here.** The figures are measured against the
seed, which is 22.9% of the corpus. `_a1_genre_cut_vs_full.ts` reports 0 of 27
endings reading the same in both bases: `-tion` is 52 in the cut and 455 in the
corpus, `-on` is 53% accurate in the cut and 74% in it. After one OTA pull a
learner has the full corpus, so the printed accuracy is wrong by up to 21 points.
Enlarging the seed is not the answer — `seed-cut.config.ts` is explicit that the
cut is a product decision, and carrying the whole corpus fights phases 14-16.
Measuring the claim against the corpus it is a claim about is the fix, and it
touches roughly sixteen coupled files. **Recommended as its own phase.**
