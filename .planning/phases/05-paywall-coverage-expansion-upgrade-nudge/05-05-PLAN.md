<objective>
Generalise the one hardcoded banner slot into a tagged union so the upgrade nudge (PAY-05) and the reconciliation notice (PAY-02 criterion 4) can share it, and so Phase 10's rating prompt can add a fourth kind later without touching this phase's code. ROADMAP Phase 5 success criterion 5 requires exactly this: one common interruption pattern shared with Phase 10, extending `PushBanner.tsx` rather than inventing an independent modal, banner or toast.

Purpose: `useUI.ts` currently holds `bannerVisible: boolean` plus `bannerAt: string`, and `PushBanner.tsx` renders exactly one message with exactly one press target (`/speak`). Two more kinds are landing in Plan 06. A `banner: BannerState | null` union is what structurally guarantees "only one banner at a time" — D-14's no-pile-up requirement becomes a property of the type rather than coordination logic somebody has to remember to write.

Output: one store field replaced, one component made kind-driven, two call sites migrated, one wiring test. **No new behaviour is added for the existing `speakReminder` kind** — this is a pure refactor plus room for two kinds Plan 06 will start using.

Note on the asymmetry you will find: `speakReminder`'s auto-hide lives in its CALLER (`useAlarmWatcher.ts`'s own `setTimeout(hideBanner, 12000)`), not in `PushBanner`. The two new kinds have no such caller-side timer, so this plan adds a component-local 10s auto-hide scoped to those kinds only. Do not "unify" the two — moving `speakReminder`'s timer would change shipped notification behaviour, which is Phase 6's territory.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| in-memory Zustand UI slot → global overlay | Process-local, non-persisted ephemeral state. Written only by app code, never by a network response or user input. |
| banner press → route push | Navigates to `/speak`, `/paywall` or `/settings`; none of these grants anything on arrival. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-22 | Tampering | `useUI.banner` slot | accept | Not persisted, not networked, process-local. The worst a tampered value achieves is showing a banner whose press target is one of three in-app routes, each of which re-evaluates its own gate on arrival. |
| T-05-23 | Denial of service | Banner pile-up starving the user of screen | mitigate | Structural, not procedural: `banner` is a single nullable field, so `showBanner` of any kind replaces whatever was there. D-14's no-pile-up requirement is now a property of the type. Additionally, the two new kinds auto-hide after 10s, and `useAlarmWatcher`'s reminder now suppresses itself while ANY banner is up (`!banner`, widened from `!bannerVisible`). |
| T-05-24 | Elevation of privilege | Banner press reaching gated content | accept | All three press targets are ungated or self-gating: `/speak` is free, `/settings` is the user's own account screen, `/paywall` sells rather than grants. `hideBanner()` runs before every push, so no banner survives into the destination. |
| T-05-25 | Information disclosure | Reconciliation banner copy | mitigate | Copy is the fixed `T.reconcileBody` string with no interpolation (D-17): it states that access ended and points to Settings, and never names a cause or an amount. Nothing about the entitlement, the plan or the billing method is rendered. |
| T-05-26 | Repudiation | Nudge taps invisible to the funnel | mitigate | `upgrade_nudge_tapped` is emitted on the nudge press path with its `trigger` prop, so nudge-to-paywall conversion is measurable. `track()` remains fire-and-forget and no-ops without a PostHog key; the banner's behaviour does not depend on it. |
