<objective>
Wire the two triggers that make PAY-05 and PAY-02's fourth success criterion true: the proactive upgrade nudge fired by a usage signal (D-11/D-12/D-13), and the reconciliation notice fired by a genuine entitlement downgrade (D-15/D-16/D-17). Both raise the shared banner slot Plan 05 built; neither introduces a new UI surface.

Purpose: today a free user only ever hears from the paywall when they are already blocked, and a user whose subscription lapses simply finds the paywall back with no explanation. This plan adds the one moment before the wall (you just used today's free role play) and the one explanation after the loss (your access has ended, here is where to fix it).

Output: one persisted timestamp field, one trigger at a scenario's completion, one statement inside an existing store branch, two test files touched.

**Deliberately out of scope, recorded rather than dropped: the coach-cap nudge.** CONTEXT.md's D-11 named "nears the coach cap" as one of two illustrative examples. 05-RESEARCH.md Pitfall 5 and Open Question 2 establish that no client-side signal for it exists: the coach cap is server-enforced and `coach.ask()` returns `{ reply, live, capped }` with no remaining-turn count anywhere in the client. Inventing a client-side counter would drift from Phase 3's `quota.ts` the moment either changed. D-11's text says "e.g." before both examples, so the roleplay trigger satisfies "a usage signal" on its own. A coach-side trigger requires a backend change (return remaining turns in the coach response) and belongs to a phase that is touching the coach edge function — it is NOT being silently descoped, it is being named here and carried into the phase's gating-rule document (Plan 07) as a known follow-up. The `BannerState` union already reserves `trigger: 'roleplay' | 'coach'` so adding it later needs no type change.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Adapty profile → `setEntitlement` | The one live write path for entitlement. Server-derived, already validated by Phase 4's `entitlementFromProfile` mapping. |
| persisted `lastNudgeAt` → nudge cadence | Local AsyncStorage, owner-writable. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-27 | Tampering | `lastNudgeAt` edited on-device to suppress the nudge forever | accept | The only effect is fewer upsell banners for the tamperer. No access, no revenue, no data integrity impact. |
| T-05-28 | Tampering | Attempt log edited to fake a spent allowance | accept | Raising the nudge early shows an upsell earlier. The actual roleplay BLOCK is a separate call (`roleplayLocked` in `start()`), which this plan does not touch, so a forged log cannot unlock a second scenario through the nudge path. |
| T-05-29 | Spoofing | Reconciliation banner raised on a false downgrade | mitigate | The banner inherits `wasDowngraded`'s two guards verbatim, because it is raised inside that exact branch: a user-id change (sign-out or sign-in swap) returns false, and an already-inactive previous entitlement returns false. Critically it is on `setEntitlement` and never on `loadFor`, so an offline cold start for a paying user reading a cached entitlement cannot raise it. Both properties are asserted in `entitlementDowngrade.test.ts`, alongside Phase 4's original five. |
| T-05-30 | Repudiation | A downgrade the user is never told about | mitigate | **This is the threat PAY-02 criterion 4 exists to close.** Before this plan, a lapsed subscriber simply found the paywall back with no explanation.
