**Install exactly one dependency and nothing else: `npx expo install @shopify/flash-list`.**

Why this is safe here, measured rather than assumed:
- The v2 tarball contains `LICENSE.md README.md dist/ jestSetup.js package.json src/` and **no `android/`, no `ios/`, no `cpp/`, no `.podspec`, no `build.gradle`, no `codegenConfig`**. Peer deps are `@babel/runtime`, `react`, `react-native` and nothing else: no gesture-handler, no reanimated.
- It is therefore **not autolinked**, and `@expo/fingerprint`'s sourcer (`build/sourcer/Sourcer.js:29-39`) hashes autolinking sources, the Expo config, CNG patches, `package.json`'s `scripts` key and the bare `android/`/`ios/` dirs. A non-autolinked JS package touches none of them, so `runtimeVersion: { policy: "fingerprint" }` (`app.json:10-12`) does not move. **No new dev client, no EAS rebuild, OTA-deliverable.** That matters because this project has had release builds die on native modules.
- v2 is **new-architecture only** and this project runs `newArchEnabled=true` (`android/gradle.properties:38`).
- Expo SDK 57 pins **2.0.2** in `node_modules/expo/bundledNativeModules.json:122`. `npx expo install` resolves it. Latest is 2.3.2; the only difference that matters here is `initialScrollIndexParams.viewOffset`, absent in 2.0.2, which costs the ability to land a restored row a few pixels below the top. **Take 2.0.2.** Do not `--force` to 2.3.2; `npx expo-doctor` will flag the mismatch.
- Run `npx expo-doctor` after installing and record its output.

**`getItemType` is what makes this work, and it is not merely nice.** FlashList recycles view instances **per type**. Without it a heading view gets recycled into an act row and back, which is exactly the churn long Android lists get blamed for. One type per `TrailRow.kind`: `orientation`, `placement`, `gate`, `heading`, `acte0`, `act`, `boundary`.

**Why not `FlatList` + `getItemLayout`:** `getItemLayout` needs every row's pixel offset known in advance without measuring. In this app row height is a function of `PixelRatio.getFontScale()` through `typeMetrics()` (`Type.tsx:116-124`), act titles wrap at unknown lengths, and headings and act rows are different heights by design. **There is no truthful `getItemLayout` to write.** Without it, `scrollToIndex` warns and needs `onScrollToIndexFailed` handling, which turns the jump-to affordance into a two-pass retry loop. FlashList v2 measures rows itself and needs **no `estimatedItemSize` at all**.

**The nesting trap.** `src/components/MissionSection.tsx:202-204` records it: *"pages its words with a horizontal FlatList, mounted inside the card, that FlatList lands inside the pager's ScrollView and React Native warns (VirtualizedLists should never be nested)"*. So the trail **cannot** live inside the `ScrollView` skeleton every other screen uses. The header, the day-one cards (plan 10) and the gate banner (plan 09) are **list items**, which is exactly why plan 04 made them row types.

**Stickiness: not in this wave (D-40).** `SectionList.js:243-244` defaults `stickySectionHeadersEnabled` to `Platform.OS === 'ios'`, a silent iOS/Android divergence. `ScrollView.js:1798-1800` forces `scrollEventThrottle: 1` whenever sticky headers exist, an `onScroll` bridge event every frame for the life of the scroll. `ScrollViewStickyHeader.js:145` carries an Android-only 15ms layout debounce. D-29's real requirement is that the jump-to affordance and the position marker are good, and neither needs stickiness. If a "which unit am I in" indicator is wanted, **one pinned chip driven by `onViewableItemsChanged`** gives the same information for one small view instead of 60 events a second.
