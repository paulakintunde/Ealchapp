# Phase 07.1 Plan 03: c2 becomes a real Level Summary

**LEVELS widened to seven members (`sons`..`c2`) across the app's type surface and the live Supabase database, with the Speak path's world/level contract pinned explicitly and the `items_level_not_c2` CHECK dropped — c2 is now expressible, not authored.**

## Accomplishments

- `LEVELS` is `['sons','a1','a2','b1','b2','c1','c2']`; every derived regex, validator and membership check (`BANDS_RE`, `unitBand`, theme `levelRange`, pack id/level) followed automatically because they derive from `LEVELS` rather than restating it.
- The Speak path's world→level mapping, previously correct only because c2 happened to append past index 5, is now pinned to an explicit `SPEAK_WORLD_LEVELS = LEVELS.slice(0, 6)`, with a real bounds check rejecting `world > 6` in its own right (not just a level mismatch).
- The two tests the plan named (`schema.test.ts`'s exclusion test, `enum-parity.test.ts`'s asymmetry test) were rewritten to assert the reversed decision, with the reversal dated and reasoned in place — not deleted.
- Live database: `drizzle/0022_content_items_allow_c2.sql` applied to `ogbothupjcivwruesgsu`, dropping the one CHECK constraint that made c2 unauthorable. `content_level` needed no migration — verified live, before and after, that it already carried c2 and was untouched.
- `TRACKS` stayed `['sons','a1','a2']` — not widened (D-32's other, deliberately separate half). `FREE_BANDS` untouched.

## Decisions Made

- Scoped exactly to D-32 as written: widen `LEVELS`, leave `TRACKS` and `FREE_BANDS` alone. No c2 content authored, none authorized.
- Where the plan's `measured_consumers` table under-listed which tests would break (three test cases outside the two it named), fixed them under Rule 1 — they are the same root cause the plan already flagged, just not individually enumerated: a test asserting the old exclusion silently starts asserting nonsense once the exclusion is reversed.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Three collateral test assertions silently inverted meaning once c2 joined LEVELS**
- **Found during:** Task 1, running the full suite after the `LEVELS` edit
- **Issue:** `schema.test.ts` had three more assertions built on c2 being excluded, beyond the two the plan's `measured_consumers` table named: a theme `levelRange` ending at `'c2'` expected to fail (now legal), a pack with matching `id`/`level`/`theme` at `'c2'` expected to fail (now legal — the actual failure it hit was a leftover theme mismatch from the fixture default, not c2), and the "every band we author is a legal unit band" + `unitBand` tests both asserted `c2` was rejected/`null`.
- **Fix:** Rewrote each to assert the new, correct behavior, with a comment dating the reversal (2026-09-24, D-32) the same way the plan's own named rewrites do.
- **Files modified:** ealch-v2/src/content/schema.test.ts
- **Verification:** `node --test src/content/schema.test.ts` — 159/159 pass
- **Committed in:** 03b7592 (Task 1 commit)

**2. [Rule 2 - Missing correctness] theme-fitness.ts's BANDS list under-counted content bands**
- **Found during:** Task 3, the required admin sweep
- **Issue:** `const BANDS = ['a1', 'a2', 'b1', 'b2', 'c1']` was a hand-copied subset of the old `LEVELS`. With `LEVELS` now carrying c2, this script's report silently stayed capped at c1 — the exact `BANDS_RE`-style drift the plan calls out by name.
- **Fix:** Imported `LEVELS` from `ealch-v2/src/content/schema.ts` and derived `BANDS` as `LEVELS.filter((l) => l !== 'sons')`, preserving the original comment's intentional exclusion of the non-CEFR `'sons'` track while picking up c2 automatically. Verified by running the script live: the report now prints a C2 column (correctly all zero, since nothing is authored there).
- **Files modified:** ealch-admin/scripts/theme-fitness.ts
- **Verification:** `npx tsx scripts/theme-fitness.ts` ran clean against the live DB, C2 column present and zero everywhere
- **Committed in:** c0fa875 (Task 3 commit)

**3. [Rule 1 - Bug] Stale comment on ealch-admin/src/db/schema.ts calling the c2 asymmetry "deliberate and permanent"**
- **Found during:** Task 3, while verifying `enum-parity.test.ts` post-migration
- **Issue:** Not in `files_modified`, but the comment directly above `contentLevel` explicitly claimed the app's `LEVELS` never carries c2 and cited `enum-parity.test.ts` as asserting "the difference is exactly c2" — both now false. The plan's own `LEVELS` rationale is explicit that a comment contradicting the code is exactly the drift this plan exists to prevent.
- **Fix:** Rewrote the comment to describe the historical asymmetry (why the enum was never narrowed) and its closure by this plan, naming both migrations (0004, 0022) and the test's new assertion.
- **Files modified:** ealch-admin/src/db/schema.ts
- **Verification:** Comment-only change; confirmed the file was not among `pnpm typecheck`'s (pre-existing, unrelated) error list before or after
- **Committed in:** c0fa875 (Task 3 commit)
