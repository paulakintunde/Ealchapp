<interfaces>
From `ealch-v2/src/content/schema.ts` (read only, do NOT modify schema.ts in this plan):
```typescript
export type LessonAct = {
  id: string;            // unique within the lesson
  title: string;
  sections: string[];    // section ids, in order
  milestone: string;     // the one line shown at the checkpoint
  estScreens: number;    // positive integer
  restPoints?: string[]; // 'sectionId' or 'sectionId/marker'
  opener?: { line: string; imageRef?: string };
};
export function validateLesson(l: unknown, path?: string): { path: string; message: string }[];
```
The validator's act block is at `schema.ts` ~L3801-3862. Three rules bite here:
1. `sectionIds` is built from `l.sections[].id` and act section refs are checked against it **only when `sectionIds.size > 0`**. The moment you give one section an id, every act ref is checked.
2. `section "<id>" is not claimed by any act` — **every** section that carries an id must belong to exactly one act. There is no partial adoption.
3. `deckTranche has N slices but there are M acts, one per act` (~L3962-3966).

Postgres shape (`ealch-admin/src/db/schema.ts:282-317`): lessons live in `content_units` with `kind='lesson'`, the whole Lesson document in `body: jsonb`, and a separate document-level `version: integer` column. **`body.version` is `Lesson.version` and is the one D-25 protects.**

Section-id convention, already in use in `sons.02.l1`/`sons.03.l1`: `s01-scene`, `s02-goals`, ... i.e. `s{NN}-{slug}`, two digits, file order, slug from the section's own subject. Reuse the two ids `sons.02.l1` already has rather than renaming them.

Act shape to copy verbatim, `sons.09.l1`:
```json
{ "id": "act1", "title": "Five rules, one sentence",
  "sections": ["s01-scene","s02-goals","s03-anchors"],
  "milestone": "The gap, named.", "estScreens": 20,
  "restPoints": ["s01-scene/end"] }
```
`deckTranche` in `sons.09.l1` is `[[], ["fr.sons.masterclass.039", ...]]` — an empty first slice is legal and already shipped.

<pipeline>
The house pipeline, from `ealch-admin/scripts/author-demonstratifs-batch.ts:1-16`:
> POSTGRES FIRST, SEED SECOND. Run merge-X-into-seed.ts after this, or the lesson exists in the database and nowhere the app can read it.
> DO NOT run content:publish from here. Publishing is not part of a lesson build, and content:parity must be read first.

Commands: `pnpm tsx scripts/author-sons-acts-batch.ts --dry` -> `pnpm tsx scripts/author-sons-acts-batch.ts` -> `pnpm tsx scripts/merge-sons-acts-into-seed.ts` -> `pnpm content:parity` -> `pnpm content:publish --dry-run`.

Known hazards on this seam, from project memory:
- The Supabase project `ogbothupjcivwruesgsu` auto-pauses from inactivity. Re-poll live status before assuming it is up; do not trust a prior status.
- `seed.json` is a CUT of the DB (roughly a quarter of Postgres). A statistic measured on the seed can be an artifact of the cut.
- **Never `git checkout` `seed.json`** to undo something. It discards other authors' uncommitted lessons. Re-run the merge instead.
- `seed.json` formatting is canonical `JSON.stringify(x, null, 2)`. A whole-file rewrite is safe; a huge git diff usually is not.
</pipeline>
