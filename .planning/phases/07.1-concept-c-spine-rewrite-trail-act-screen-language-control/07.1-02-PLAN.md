Purpose: D-38 is the only load-bearing library claim in the research with a contradiction under it. Two sources disagree: expo-router's vendored `native-stack/types.d.ts:609` says formSheet "falls back to modal on Android", the shipped react-native-screens 4.26.2 Kotlin says it uses Material `BottomSheetBehaviour`. The whole Fiche-sheet and pre-roll-sheet approach (D-02, D-12) rests on which is true.

**Audited 2026-09-24, before execution. The source now points one way, and the device session is confirmation rather than discovery.** In the installed react-native-screens 4.26.2: `Screen.kt` declares `StackPresentation.FORM_SHEET` and branches on it (`:307`, `:589`, `:608`); the JS layer sets sheet defaults in `components/Screen.js:41-53` with **no** `Platform.OS` branch, and the only iOS gates in `components/ScreenStackItem.js` are cosmetic (header-in-modal `:40`, `contentStyle` `:54`, an iOS 26 case `:162`) — `stackPresentation` is never rewritten for Android. And `android/build/.transforms/.../com/swmansion/rnscreens/bottomsheet/BottomSheetDialogScreen.dex` exists, so the Material sheet implementation is compiled into THIS project's build output, not merely present in the package. The "falls back to modal" comment reads as stale for 4.26.2. **This is strong static evidence, not runtime proof** — still run the check, but expect it to confirm, and if it does NOT, that contradiction is itself the finding and the fallback branches in plans 05, 06 and 09 take over.

D-17 is the same discipline one layer up: extending an unproven two-state base to three states makes the first device failure ambiguous between the shipped work and the new third state.
