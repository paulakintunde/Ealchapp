<objective>
Wire the client to the server gate (D-07): a real entitlement check on the paper screen, an awaited authorization call before the runner opens, and an attempt reference on every grading request.

Purpose: D-07 is defense-in-depth with a concrete UX purpose — "block starting a premium exam client-side rather than letting someone complete a whole exam only to have grading refuse it." Today `app/exam-paper.tsx` imports no entitlement anything: the only lock is one screen up, on the paper list (`app/exam.tsx`), so a deep link or a back-navigation onto an already-open paper screen bypasses it entirely. And `examGrader.grade()` sends no `paperId`/`skill`, so `grade-exam` has nothing to validate an attempt against.

**Known accepted limitation, to be carried forward explicitly:** when the start call is unreachable (offline, or a 5xx), the candidate is allowed into the runner anyway — an authorization service that is down must not cost someone their sitting, and today's behaviour is that an offline candidate with cached clips can sit a paper. The residual is that under a future `examGateOn: true`, an attempt begun while offline may have no authorization row and be refused at grading. `exam-section.tsx` re-issues the idempotent start call on mount to shrink that window, but it does not close it. This must be resolved before the paywall flag is flipped — Phase 5 owns that flip, and 04-08's SUMMARY must hand this to it as a named prerequisite.

Output: a small `startExamAttempt` service, its ENV slug, `paperId`/`skill` threaded through grading, both client gates in `exam-paper.tsx`, and source-text tests that the wiring exists.
</objective>

```typescript
//
// The client already has an opinion about entitlement (useEntitlement, fed by
// the Adapty profile) and that opinion gates the UI. This call is the one that

// will trust at submit time.
//
// Three distinct answers, because the caller must treat them differently:
//   'authorized'  -> open the runner.
//   'refused'     -> do NOT open the runner; the reason says where to send them
//                    (the paywall for needs-exam-tier, sign-in for
//                    auth_required). Refusing here is the whole point of D-07:
//                    a candidate must not sit a whole épreuve only to have
//                    grading turn it down.
//   'unreachable' -> the authorization service could not answer. The caller
//                    proceeds, deliberately. An offline candidate with cached
//                    clips can sit a paper today, and a service outage must not
//                    take that away. See the accepted limitation in
//                    .planning/phases/04-.../04-07-PLAN.md — this must be
//                    revisited before examGateOn is ever flipped to true.
//
// Never throws, on the same principle as examGrader.grade(): every outcome is a
// real answer the caller has to handle, not an exception to swallow.
```

Exports, exactly:

```typescript
export type StartAttemptResult =
  | { status: 'authorized'; expiresAt: string; gateOn: boolean; entitled: boolean }
  | { status: 'refused'; reason: string }
  | { status: 'unreachable' };

export async function startExamAttempt(req: {
  paperId: string;
  skill: string;
  mode: string;
}): Promise<StartAttemptResult>;
```

Implementation:
- `const sb = supabase(); if (!sb) return { status: 'unreachable' };`
- `try { const { data, error } = await sb.functions.invoke(ENV.startExamAttemptFunction, { body: { paperId: req.paperId, skill: req.skill, mode: req.mode } }); … } catch { return { status: 'unreachable' }; }`
- On a successful invoke where `data?.ok === true` and `typeof data.expiresAt === 'string'`: return `{ status: 'authorized', expiresAt: data.expiresAt, gateOn: !!data.gateOn, entitled: !!data.entitled }`.
- Distinguishing a refusal from an outage: `supabase-js`'s `functions.invoke` surfaces a non-2xx as an `error` of type `FunctionsHttpError` carrying the response. Read the body with `await error.context.json()` inside its own `try/catch`; if that yields a `reason` string, return `{ status: 'refused', reason }`. If the body cannot be read, or the error is a `FunctionsFetchError`/network failure with no HTTP status, return `{ status: 'unreachable' }`. Comment this branch: `// A 4xx is a DECISION; a network failure is an absence of one. Collapsing the two would either strand offline candidates or let a refused one sit anyway.`
