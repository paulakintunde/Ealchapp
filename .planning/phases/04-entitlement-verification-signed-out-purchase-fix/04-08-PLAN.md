  <what-built>
No code was changed for this scenario, deliberately. `syncIdentity()` in `src/services/purchases.ts` already does what D-02 hopes it does — `await A.identify(userId)` fully resolves before `await A.getProfile()` is issued, and `getProfile()` is documented to query the API rather than serve a cache:

```typescript
async function syncIdentity(userId: string | null): Promise<void> {
  await useEntitlement.getState().loadFor(userId);   // cache-first, offline-honest
  if (!configured) return;
  const A = loadModule()!;
  try {
    if (userId) await A.identify(userId);
    else await A.logout();
    await apply((await A.getProfile()) as ProfileLike);
  } catch { /* identity sync failing must not strand the UI */ }
}
```

What vendor documentation does NOT state is whether `identify()`'s promise resolves only once the server-side profile switch is complete and queryable, or on request acceptance with the switch completing asynchronously — which would produce exactly the stale pre-merge read ROADMAP's Pitfall Watch warns about. RESEARCH.md logs this as assumption A1 and routes it here, to observation. One closed-without-resolution upstream issue (AdaptySDK-React-Native #108) reports a stale purchase record after `identify()` when switching sandbox accounts, which is why documentation is not being accepted as proof.

This checkpoint is the test. Skip it only if Task 1 reported this build cannot sell.
