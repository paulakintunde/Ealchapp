<objective>
Make a premium→free entitlement transition a loud, logged, monitored event (D-08), app-wide — covering exams, coach, roleplay and content gates uniformly, not just the exam path.

Purpose: ROADMAP Phase 4's Pitfall Watch requires that "any entitlement state flip (premium→free)" be "a loud, logged, monitored event, not a silent cache-miss." Today nothing observes the transition at all, so a user losing access looks identical to a user who never had it.

Output: a pure `wasDowngraded` predicate in `entitlement.logic.ts` with its own tests, a new `entitlement_downgraded` member of the `AnalyticsEvent` union, and detection wired into `useEntitlement.setEntitlement` — the live Adapty-derived write path ONLY.

**The hazard this plan must not create:** hooking detection in `loadFor` (the cache-read path) would fire a false downgrade on every offline cold start, which is exactly the user ROADMAP Success Criterion 3 protects. `loadFor` must stay untouched.
</objective>

**A. Add the predicate to `ealch-v2/src/store/entitlement.logic.ts`.**

Place it immediately after the existing `isPremium` function (around line 132), keeping the file pure (no new imports). Add it verbatim:

```typescript
/** Phase 4 / D-08: did this write LOSE a paying user their access?
 *
 *  The whole point is that the answer is loud (see useEntitlement's
 *  setEntitlement, which is the only caller). Two cases deliberately answer
 *  NO, because reporting them would make the signal useless:
 *
 *  - A different user id. An entitlement write during a sign-in or sign-out is
 *    a change of WHO, not a loss of what. purchases.ts's apply() keys the new
 *    entitlement on the current uid (ANON_USER when signed out), so every
 *    sign-out would otherwise read as a premium user being downgraded.
 *  - A previous entitlement that was already inactive at nowMs. An expired
 *    subscription being written as 'free' is bookkeeping catching up, not
 *    access being taken away — isPremium was already false before the write.
 *
 *  Not hooked on the CACHE read path (loadFor) on purpose: an offline cold
 *  start legitimately reads a cached entitlement, and firing there would flag
 *  every launch of an offline paying user — the exact user ROADMAP Phase 4
 *  Success Criterion 3 exists to protect. */
export function wasDowngraded(prev: Entitlement, next: Entitlement, nowMs: number): boolean {
  if (prev.userId !== next.userId) return false;
  return isPremium(prev, nowMs) && !isPremium(next, nowMs);
}
```

Do not change any existing function in this file.

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-11 | Information Disclosure | the `entitlement_downgraded` event payload | mitigate | Props are limited to `fromPlan`, `toPlan` (plan-name enums already sent with `plan_selected`/`purchase_completed`) and a boolean `hadExpiry`. | T-04-17 | Denial of Service (alert fatigue / false signal) | detection hooked on the cache-read path | mitigate | Detection lives only in `setEntitlement`; `wasDowngraded` additionally returns false on a user-id change and on an already-inactive previous entitlement. Enforced by a source-text test asserting `loadFor`'s body contains no `entitlement_downgraded`. A monitoring signal that fires on every offline launch would be worse than no signal. |
| T-04-18 | Repudiation | a silent loss of access with no record | mitigate | This plan IS the mitigation: the flip becomes an emitted event rather than an unobservable cache state. Accepted residual: with `EXPO_PUBLIC_POSTHOG_KEY` unset, `track()` is a documented no-op and the event is lost — consistent with every other funnel event in this codebase, and not worth a local durability queue that would claim persistence it lacks (`analytics.ts`'s own header states this trade). |
| T-04-06 | Known accepted limitation | webhook-lagged entitlement mirror producing a transient flip | accept | D-04's explicit trade-off. The client's entitlement is Adapty-profile-derived, not mirror-derived, so a lagging `adapty-webhook` cannot itself drive a client-side downgrade event; a genuine store-side lapse can, and should. No mitigation attempted, no live Adapty API call added. |
