<objective>
Make all three notification toggles true. `notifs.report` and `notifs.nudge` have never been read by anything (confirmed in 06-CONTEXT.md D-01); this plan gives each one a real local-notification consumer, replaces the last blanket cancel on a per-toggle path, and re-arms the schedule from the toggles at every launch.

Purpose: this is NOTIFY-01 and ROADMAP Success Criterion 1, taking the "build both" fork the user chose over retiring the toggles. The report fires shortly after a session ends (D-04) and the nudge fires on a fixed weekly cadence with generic copy (D-05/D-06), both as real device notifications (D-03) so Phase 17's tap-to-deep-link lands uniformly on all three kinds later.

The one structural trap: the obvious place to trigger the report is `useSessionLog()` in `useProgress.ts`, but `useStore.ts` already imports `useProgress.ts` and says so in a comment at line 13. Adding the reverse import would make that comment false and create a real module cycle. So the dependency is INJECTED — `useProgress` exposes a setter, `useStore` (which already depends on it) registers the handler. The arrow keeps pointing one way.

Non-goal, deliberately: `app/settings.tsx` and `app/onboarding.tsx` need no edit. Both already render all three rows generically off `T.notifLabels` and call `setNotif(key, v)`; the toggles were never broken at the UI layer, only unconsumed at the store layer. Extracting their duplicated `['daily','report','nudge']` tuple into one shared constant is an allowed-but-optional tidy-up (06-PATTERNS.md) and is not done here.

Output: the store gains three real toggle branches plus a launch-time resync, the progress store gains one injection point, and the D-07 guard is extended to cover the two new templates.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| persisted toggle state → OS scheduler | `notifs` is a per-device preference in AsyncStorage. It gates only local notification scheduling; no server reads it and no entitlement depends on it. |
| session-end event → notification scheduling | The listener runs in-process, fired by the same callback that writes the session log. It carries no user-entered text. |
| OS notification permission | Requested through the existing `requestPermissions()`; a denial is honoured by reverting the toggle, never worked around. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-13 | Denial of service | `setNotif` toggle-off path | mitigate | The failure this plan most has to avoid is one toggle silencing the others. Every toggle-off calls `notifications.cancelKind(k)`, which touches only that kind's identifiers; `cancelAll()` remains reachable from `eraseLocalData` alone, asserted by `grep -c "notifications.cancelAll()"` returning exactly 1. |
| T-06-14 | Tampering | `resyncNotifs` running on every launch | accept | It only reschedules what the local toggles already say and cancels what they say is off. Worst case for a user who edits the persisted blob is that their own device reminds them differently — no access, no revenue, no server state is touched. |
| T-06-15 | Information disclosure | Report notification on a locked screen after a session | mitigate | `reportBody` interpolates only the coach display name (Plan 01 locked the template to a single `{name}` token, and the guard test fails if a second token appears). No score, streak, weak-spot or account detail is placed in the body, so the notification cannot leak a learner's performance to someone glancing at their lock screen. |
| T-06-16 | Elevation of privilege | Permission-denial handling | mitigate | On native denial the toggle is set back to false rather than retried or worked around, matching the existing `daily` contract (06-UI-SPEC.md Permission-denial state). The app never schedules against a permission it was not granted. |
| T-06-17 | Repudiation | Session log vs notification scheduling | mitigate | The listener fires AFTER `logSession` and is wrapped in try/catch, so a scheduling failure can never roll back or prevent the record that the user practised. |
| T-06-18 | Spoofing | — | accept | No auth, session or identity surface in this phase (06-RESEARCH.md Security Domain: V2/V3/V4/V6 not applicable). |
</threat_model>
