# Phase 6 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope Note (read first)

This phase is **behavioral/logic wiring, not new visual design**. Confirmed by direct code read:

- `app/settings.tsx`'s `ToggleRow` (lines 47-82) and `app/onboarding.tsx`'s equivalent 3-toggle list already render the report/nudge/daily rows. This phase makes those toggles functionally trustworthy (wired to real per-kind scheduling per NOTIFY-01); it does **not** touch `ToggleRow`'s markup, layout, spacing, or the `Toggle` component.
- `PushBanner.tsx`'s visual presentation (card shape, colors, animation) is unchanged. Only the body text content correctness changes (NOTIFY-02), via the new shared `formatNotifText` function both it and `useStore.ts`'s scheduler will call.
- No new screens, components, icons, or layout are introduced. `components.json`/shadcn is not applicable — this is a React Native/Expo app, not a React/Next.js/Vite web stack, so the shadcn initialization gate in the researcher's own instructions does not apply here.

**Per the phase brief's own instruction:** this UI-SPEC is deliberately minimal. It locks the one thing this phase actually authors — new notification body copy (FR/EN) for `reportBody`/`nudgeBody` — plus one small, justified microcopy correction to existing `notifLabels` sub-text that the phase's own trigger-design decision (D-04) makes stale. It does not fabricate new spacing/color/typography decisions this phase has no surface for.

## Copywriting Contract

This is the one real authoring surface this phase owns: new `reportBody`/`nudgeBody` i18n templates (FR/EN) for the shared `formatNotifText` function to route through, plus one existing-string correction. All copy below follows the project's standing style rules (no em dash in user-facing strings — colon is the established separator, as already used in `bannerText`; no use of the word "honest"). Voice/tone matched to the existing `bannerText` precedent (`'Votre séance de {t} vous attend : Au Café, 4 min avec {name}.'`) — warm, concrete, second person, colon-separated clause.

### New template: `reportBody` (fires per-session, per D-04)

| Lang | Copy |
|------|------|
| FR | `Votre rapport est prêt : découvrez comment s'est passée votre séance avec {name}.` |
| EN | `Your report is ready: see how your session with {name} went.` |

Placeholder: `{name}` → `avatarName(get().avatarId)`, mirroring the existing pattern `PushBanner.tsx` already uses for `bannerText`'s `{name}`. No `{t}` placeholder — the report fires a short, fixed delay after session end (Pattern 5, `TIME_INTERVAL`, not a fixed clock time), so there is no meaningful "at {t}" to state.

### New template: `nudgeBody` (fires periodically, generic encouragement, per D-05)

| Lang | Copy |
|------|------|
| FR | `Deux minutes suffisent pour progresser : {name} vous attend pour un micro-défi.` |
| EN | `Two minutes is enough to make progress: {name} is ready for a quick micro-challenge.` |

Placeholder: `{name}` → same `avatarName(get().avatarId)` resolution. Deliberately generic per D-05 — no reference to a specific tracked weak spot (no such pipeline exists; out of scope). Matches the existing `notifLabels` sub-label tone: "Micro-défis de confiance, sans streak" / "Micro-challenges, no streaks."

Both new templates go in `strings.ts` beside `bannerText` (both `fr` and `en` blocks, same key order) — required for the existing `i18n.test.ts` key-parity guard (`collectKeys` deep-equal across `fr`/`en`) to have something to check, per RESEARCH.md's Anti-Patterns note.

### Existing string correction: `notifLabels[1].sub` (the "report" row's sub-label)

**Why this needs a copy change, not just logic:** The currently-shipped sub-label reads `'Votre rapport, chaque soir après la séance'` / `'Your report, each evening after the session'` — this literally promises a fixed *evening* delivery time. D-04 resolves the report's actual trigger to option (a): fire shortly after **any** session ends, whatever time of day that is. Leaving the existing "each evening" wording in place after this phase ships would make the Settings screen itself state something false about the notification it now correctly, functionally delivers — a correctness regression this phase would otherwise have introduced silently. This is a one-line microcopy fix inside the toggle row this phase already touches structurally (D-01: wiring the same row to a real scheduler), not a new UI surface.

| Lang | Old | New |
|------|-----|-----|
| FR | `Votre rapport, chaque soir après la séance` | `Votre rapport, juste après la séance` |
| EN | `Your report, each evening after the session` | `Your report, right after your session` |

`notifLabels[0]` (daily) and `notifLabels[2]` (nudge) sub-labels are accurate as shipped and are **not** changed.

### CTA / empty state / destructive action

Not applicable — this phase adds no new screen, no new primary action button, no empty-data state, and no destructive action. The toggles this phase wires are pre-existing UI (`Toggle` on/off), not a new CTA.

### Permission-denial state (closest thing to an "error state" this phase touches)

Reuses the existing, established pattern exactly — no new copy, no new UI. Per `useStore.ts:238-245`'s `enableDailyReminder` (the pattern the new `report`/`nudge` `setNotif` branches must mirror per RESEARCH.md's Open Question #2 recommendation): if the OS denies the notification permission, the toggle silently reverts to its `off` visual state. No toast, no alert, no error string is shown today for `daily`, and this phase does not introduce one for `report`/`nudge` either — consistency with existing behavior is the correct contract here, not new error messaging design.
