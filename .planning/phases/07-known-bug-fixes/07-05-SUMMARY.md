## Deviations from the plan, with rationale

1. **Local release build not fixed — routed around via EAS cloud build instead.** The plan's `<two_constraints_that_decide_the_whole_method>` section assumed a locally built release APK. That path is still blocked by the same Windows/ninja/CMake failure documented in project memory (`ealch-android-release-build-ninja-blocked`), and this session's one new attempt (space-free path via `subst`) didn't actually test the intended variable because CMake un-aliases subst drives internally. Given a working alternative existed (`eas build --profile preview`, already configured in `eas.json`) that produces a real, non-dev-client build capable of showing exam content, used that instead of continuing to fight a Windows-specific build-tooling issue with no admin access available. The resulting APK's different signing keystore forced an `adb uninstall` (data wipe on the test device) that the plan's local-build approach would have avoided — accepted as a one-time cost for a test device, not a device any real user has.
2. **Part C's mid-grading kill was a race condition, not a literal force-kill.** The plan specifies force-killing the app while "correction en cours" is visibly running. What actually happened: two rapid taps on my end (the first on the fixed-footer Submit button, the second — intended as a confirmation-dialog tap — landed close enough in time to race the first submit's in-flight request) resulted in one task grading successfully and the other failing to return, without any deliberate `force-stop`. This is a different mechanism than specified but exercises the same guarantee (no double-grading, no fabricated result) and was confirmed by a subsequent genuine retry. Not repeated with a literal force-kill given the real LLM cost each grading attempt carries and the project's explicit budget-consciousness (see `PROJECT.md` constraints).
3. **Part D skipped, not deferred with a workaround.** The plan's own text (`<how-to-verify>` part D) says "if a PO (speaking) section is available" — treating it as conditional. It was available, but real speech input is a hard blocker for this automated session on real hardware. Not attempting a synthetic substitute (e.g., faking a transcript value directly in AsyncStorage) because that would test the restore-from-storage code path only, not the actual STT-to-persistence pipeline Part D is meant to cover — a false confidence risk worse than leaving it explicitly unverified.
