# Architecture Research — Integration Plan for This Milestone's Fixes

**Domain:** Mobile French-learning app (Expo/React Native + Supabase), subsequent-milestone integration research
**Researched:** 2026-09-19
**Confidence:** HIGH (all findings verified by reading the actual current source, not the codebase-map summary alone — several corrections to `CONCERNS.md` below are load-bearing for phase planning)

## IMPORTANT: Corrections to `.planning/codebase/CONCERNS.md`

`CONCERNS.md` was written from a static audit and, on five points relevant to this milestone, describes a state that the live code has already moved past. Re-reading the actual files changes what the roadmap needs to plan for. Each correction below cites the file/lines that prove it.

1. **The content-publish drift guard already exists and already blocks the exact incident class described.** `ealch-admin/scripts/publish-content.ts` step "4·0 RULE no-silent-regression" (lines ~560-655) diffs `git show HEAD:ealch-v2/src/content/seed.json` lesson bodies against what is about to publish from Postgres, and **refuses to publish** (`process.exit(1)`) if any committed lesson would be deleted or reverted to a lower version. It runs on `--dry-run` too. This is not "a manual discipline enforced by a checklist" — it is code, already shipped, already the reason a publish dies today rather than silently destroying content. **What CONCERNS.md got right:** the recovery step (`restore-lesson-bodies-from-seed.ts`) is still a manual, separately-invoked script — the guard blocks, it does not self-heal. **What's still a real gap:** the guard only compares `Lesson.body` (via `content_units` rows of kind `lesson`). It does NOT compare units, scenarios, playlists, speak stages, domains/themes, or exam papers/tasks authored seed-direct — a seed-direct edit to any of those ships fine today but is just as vulnerable to being silently overwritten on the next publish, with no guard and no refusal. That is the actual remaining scope for "Reliability: pre-publish content-drift guard" in `PROJECT.md`.

2. **Entitlement already syncs cross-device — via Adapty, not Postgres directly — and this substantially covers "purchases survive reinstall/new device."** `ealch-v2/src/services/purchases.ts` (`useEntitlementSync`, `initPurchases`, `syncIdentity`) activates Adapty with `customerUserId: <Supabase auth uid>` and reconciles the entitlement on every foreground and every sign-in/out (`AppState` listener + `useStore.subscribe` on `userId`). A signed-in user who reinstalls or switches devices and signs back in already gets their Première/exam entitlement back via Adapty's own cloud profile keyed to their Supabase uid — this is not "lost forever" as `CONCERNS.md`'s "Cross-device entitlement sync" item claims. There is also a Postgres mirror (`entitlements` table, written by `ealch-v2/supabase/functions/adapty-webhook/index.ts`) — but it is explicitly documented as advisory-only, never a runtime authority (`useEntitlement.ts` comment: "the client NEVER reads them to grant access"). **What's still a real gap:** (a) a user who purchases while signed OUT (`ANON_USER` cache key, ANON Adapty profile) has no `customerUserId` to identify by, so that purchase is stranded on the anonymous Adapty profile and never migrates to their account if they later sign in on a different device; (b) `sync.ts` (the progress-sync module) genuinely has zero entitlement references, so there is no path for the app's own backend logic (grading limits, `coach.unlimited` server-side exemption) to read entitlement from anywhere except the advisory webhook mirror, which the `coach` edge function already leans on per its own comment. The gap is narrower than CONCERNS.md states: it's "signed-out purchases" and "server-side feature gating consistency," not "entitlement sync doesn't exist."

3. **The OTA snapshot ceiling is 50 MiB, not 30 MiB, and it is served from a public Supabase Storage bucket, not an edge function.** `ealch-v2/src/services/content.logic.ts:732`: `export const MAX_SNAPSHOT_BYTES = 50 * 1024 * 1024;` — raised twice (4→30 MiB on 2026-07-28, 30→50 MiB on 2026-09-07), both documented as deliberate, both noting the real constraint moved from transfer to in-memory `JSON.parse` cost. There is **no** `content-snapshot` Supabase Edge Function anywhere in the repo — `ealch-admin/supabase/functions/` and `ealch-v2/supabase/functions/` both were checked; the real functions are `adapty-webhook`, `coach`, `delete-account`, `grade-exam`, `tts`. The snapshot is a static file (`snapshots/v{n}.json` + `manifest.json`) in a public Storage bucket, fetched directly by the client (`content.ts` `STORAGE_BASE = .../storage/v1/object/public/content`, `refreshFromRemote()`). Any "content-snapshot function" work in the milestone brief needs to be understood as **Storage bucket layout + manifest schema + client fetch logic**, not an edge function to modify.

4. **The AsyncStorage 6 MB ceiling problem is already fixed.** The cache was moved off AsyncStorage onto the filesystem (`expo-file-system` `File`/`Paths`) specifically because of the v66 27 MB-vs-6MB incident — this is documented in detail in `content.ts` lines 12-36 ("It was AsyncStorage, and at v66 the snapshot reached 27 MB against the 6 MB... budget... Nothing looked broken... A multi-megabyte blob is what a file is for"). The remaining scaling risk is the 50 MB `JSON.parse`/`stableStringify` in-memory cost on low-end Android, and the download itself is already streamed to disk (`File.downloadFileAsync`), not buffered in memory. So "snapshot too big for AsyncStorage" is resolved; what's open is "snapshot too big to parse/hold as a JS string on a low-end device," and — separately — a first-run learner unconditionally downloads the full 50 MB blob (all levels, exam content included) even if they only ever touch A1. That second point is the real argument for level-splitting, not the AsyncStorage ceiling.

5. **The bundled-seed cut is already split by curriculum level/track conceptually** (`ealch-admin/scripts/seed-cut.config.ts` — `SEED_CUT.tracks: ['sons','a1','a2']`, prereq-closed, themes-gated). This is the pattern to extend to the OTA snapshot itself, not a pattern to invent from scratch.

These corrections change phase scoping (see "Suggested Build Order" below) — several items in `PROJECT.md`'s Active requirements are narrower, lower-risk "close the gap" work rather than "build from zero," and the roadmap should reflect that.

## Fix 1 — Content-publish safety (drift guard extension)

**Current state (already built):** `publish-content.ts` step 4·0 hard-blocks any publish that would delete or revert a committed lesson body. It reads the committed seed via `git show HEAD:...`, compares `Lesson.version`/section count per lesson id, and dies with an actionable message pointing at `restore-lesson-bodies-from-seed.ts` before touching Storage or the DB counter.

**Concrete integration point for the remaining gap:** the same step 4·0 block in `publish-content.ts` (lines ~560-655), generalized. Today it only builds `live = new Map(lessons.map(l => [l.id, l]))` from `content_units where kind='lesson'`. The fix is to run the identical "committed-vs-about-to-publish" comparison for the other `content_units` kinds that can be authored seed-direct: `curriculum_unit`, `scenario`, `playlist`, `speak_stage` (all read at step 1 of the same script, already in scope as `units`, `scenarios`, `playlists`, `speakPath`). Since all four already have a `version`-bearing or list-shaped body read from the same query block, the same "for each committed body, does the about-to-publish DB body exist and is it >= as rich" pattern generalizes directly — this is a data-shape problem (each kind needs its own "richness" comparator: unit → lessonIds.length, scenario/playlist → some size/version field, speak_stage → block count), not a new subsystem.

**Data flow change:** none externally visible — this is entirely inside `publish-content.ts`, before any Storage write. No schema change, no new table. The only new artifact is the comparator functions per content kind.

**Build order:** Do this FIRST, before entitlement/snapshot/cold-start work, and treat it as its own single-phase, low-risk change. It touches only `ealch-admin/scripts/publish-content.ts` (plus maybe extending `restore-lesson-bodies-from-seed.ts` for the newly-covered kinds), has zero mobile-app surface, and is testable by re-running `pnpm content:publish --dry-run` against a deliberately stale-DB fixture. It has no dependency on any other fix in this milestone. It's also the highest-leverage fix given the project's history (the one actual data-loss incident on record), so front-loading it de-risks every other seed-direct authoring that happens while the rest of the milestone is built.

**Blast radius if done wrong:**
- *Too narrow (current state, doing nothing further):* silent data loss stays possible for scenarios/playlists/speak stages/units authored seed-direct — same failure class as the 2026-07-31 incident, just on different content kinds. Low probability (seed-direct authoring is mostly used for lessons per project memory) but the exact failure mode that already burned this project once.
- *Too aggressive (e.g., making the guard fail-closed on ANY discrepancy, not just loss):* every legitimate DB-ahead-of-git publish (the normal case) would need a matching git commit first, freezing the publish pipeline. The existing guard is deliberately asymmetric (DB-ahead-of-git is fine and unremarked; git-ahead-of-DB is the only refusal) — any extension must preserve that asymmetry or it will block routine, safe publishes and someone will "fix" it by disabling the guard entirely, which is worse than not extending it.
- *Getting the git-read wrong:* the guard already handles "no git/no HEAD" as a warning-and-skip, not a hard fail (so a fresh clone / CI without history doesn't wrongly block). Any extension must keep that same graceful-skip, or a CI environment without full git history starts failing all publishes.

## Fix 2 — Entitlement sync

**Current state (already built):** Adapty is the runtime entitlement authority, keyed to the Supabase auth uid via `customerUserId`. `purchases.ts` `useEntitlementSync()` (mounted once in `app/_layout.tsx`) reconciles on boot, on every foreground (`AppState` listener), and on every `userId` change (`useStore.subscribe`). The local cache (`services/entitlement.ts`, AsyncStorage keyed `ealch-entitlement:<userId>`) is what makes this offline-honest — screens read `useEntitlement`/`useFeature`, never Adapty directly. A Postgres mirror (`entitlements` table) exists via `adapty-webhook`, explicitly advisory/analytics-only.

**Concrete integration points for the real remaining gaps:**

1. **Signed-out purchase stranding.** `apply()` in `purchases.ts` writes the cache under `useStore.getState().userId ?? ANON_USER`. If a user purchases while `userId` is null, the Adapty profile that owns the purchase is Adapty's own anonymous profile, not one identified by any Supabase uid. `syncIdentity()` calls `A.identify(userId)` on sign-in, which Adapty documents as merging the anonymous profile into the identified one — so the actual gap may already be handled by Adapty's own `identify()` semantics, and needs verification rather than new code. **Integration point:** `syncIdentity()` in `purchases.ts` (lines ~108-122) — the fix, if needed, is ensuring `identify()` is called at the moment of sign-in (already done via the `useStore.subscribe` in `useEntitlementSync`) and adding a post-identify `refreshEntitlement()` call to pull the merged profile immediately rather than waiting for the next foreground (this one is a small, safe addition: call `apply()` after `A.identify()` succeeds, which `syncIdentity` already does).
2. **Server-side feature gating consistency.** `grade-exam`/`coach` edge functions need a reliable way to check entitlement server-side (e.g., is this user's `coach.unlimited` active right now) without trusting the client. **Integration point:** the existing `entitlements` table (webhook-fed) is the only server-side source today, and it's advisory by design — promoting it to "trusted enough for server-side gating" means either (a) accepting webhook lag as a known limitation documented in the fix, or (b) adding a Postgres RPC that calls Adapty's server API directly for a real-time check inside the edge function, which is a new integration (Adapty server SDK/API key in the edge function environment) rather than a mobile-app change. This is the one piece of "entitlement sync" that is genuinely new work, not an extension of existing plumbing.

**Data flow change:** For (1), none — reordering an existing call. For (2), new: an edge function (`grade-exam` or wherever server-side entitlement checks are needed) gains a call to Adapty's server API or a freshness check against `entitlements.updated_at`, which is a new dependency edge (edge function → Adapty API) that doesn't exist today.

**Build order:** Independent of Fix 1, Fix 3, and Fix 4 — different files, different subsystems, no shared state. Sequence internally: verify/fix (1) first (cheap, mobile-only, testable by hand: purchase signed-out, sign in, confirm entitlement follows) before touching (2), since (2) requires deciding whether server-side trust-the-webhook-mirror is acceptable for this app's risk profile (coach/exam grading cost exposure) — a product decision, not just an engineering one, and worth a roadmap phase of its own if pursued.

**Blast radius if done wrong:**
- *Signed-out purchase fix done wrong (e.g., double-granting):* a bug in the identify/merge sequence could result in a user's entitlement not following them (revenue-visible, but self-healing — `restorePurchases()` exists and the paywall already has a "Restore" control) or, worse, could double-count/duplicate grants if `apply()` is called twice concurrently — `apply()` is not guarded against concurrent invocation the way `syncAttempts` in `sync.ts` uses an `inFlight` flag. Low risk (Adapty's own profile is authoritative; the risk is UI staleness, not incorrect billing) but worth adding the same `inFlight` guard pattern from `sync.ts` if this becomes a frequent call site.
- *Server-side gating done wrong:* if the edge function trusts a stale webhook mirror row for a real cost-bearing decision (e.g., unlimited coach turns), a lapsed subscriber could get free unlimited access until the next webhook event — a cost/business risk, not a crash risk. This is exactly why the existing code comment insists the mirror stays advisory; any change here should be scoped narrowly (e.g., only gate the specific expensive server operations, not general access) and reviewed against that comment's intent rather than casually promoting the mirror's authority everywhere.

## Fix 3 — Content snapshot scaling (split by curriculum level)

**Current state:** One snapshot per publish (`snapshots/v{n}.json`), one `manifest.json`, both in a public Storage bucket, `MAX_SNAPSHOT_BYTES = 50 MiB`. The seed bundled in the binary is already a level/track-gated cut (`seed-cut.config.ts`) of the same corpus, but the OTA snapshot a device fetches over the network is the FULL corpus (all levels + all exam content) in one blob.

**Concrete integration points:**

1. **Publish pipeline (`ealch-admin/scripts/publish-content.ts`):** step 5 ("The seed cut") already computes `seedUnits`/`seedLessons`/`seedItems`/etc. filtered by `SEED_CUT.tracks`/`themes`/`speakWorlds`. Splitting the OTA snapshot means generalizing this same filter machinery to produce N corpus-shaped objects (e.g., `snapshot-a1.json`, `snapshot-a2.json`, `snapshot-exams.json`) instead of one `corpus` object, each independently `validateCorpus()`-checked (the corpus-in-its-own-right validation the seed cut already gets at line ~995), each with its own checksum, each uploaded to its own Storage path. Step 6 (bytes/checksum) and step 8 (upload) both need to become per-split rather than singular.
2. **Manifest schema (`content.logic.ts` `Manifest` type, `isManifest()`):** currently `{version, path, checksum, rollout?}` — a single `path`. Splitting requires either (a) one manifest listing multiple `{level, path, checksum}` entries, or (b) one manifest per level at a predictable path (`manifest-a1.json`, `manifest-a2.json`). Either choice is a breaking change to `isManifest()` and every manifest consumer — must ship with backward-compatible parsing (old cached devices reading a new-shape manifest must fail closed to "no update available," not crash) exactly the way `isManifest` already fails closed on a malformed `rollout` field today.
3. **Mobile content loading (`ealch-v2/src/services/content.ts` `refreshFromRemote()`):** currently fetches one manifest, one snapshot, merges into one corpus. Splitting means: fetch a per-level manifest only for levels the user actually needs (e.g., their current level + one ahead, from `useStore.level`/progress), download only those snapshot files, and `mergeCorpus()` each on top of the seed. This is the biggest data-flow change of the whole milestone — `cachedSnapshotVersion` (currently one number) becomes per-level state, `shouldAdopt()` needs a per-split call, and the cache file layer (`snapshotFile()`, currently one file) becomes one file per split.
4. **Exam content**, which today ships snapshot-only and is fetched as part of the same single blob, becomes its own natural split (it's already excluded from the seed cut for exactly this "don't bloat every install" reason — extending that same logic to the OTA layer is the most natural first split to implement, since the Examiner screen already tolerates "no exams available yet" as a real, tested state).

**Data flow change:** `cachedSnapshotVersion: number` → `Record<string, number>` keyed by split; `snapshotFile()` → per-split file; `refreshFromRemote()` → loop over needed splits rather than one fetch. `mergeCorpus(SEED, adopted)` already supports overlaying a partial corpus onto the seed (this is exactly what it does today for the single-snapshot case), so multiple sequential `mergeCorpus` calls (seed → split A → split B) should work with the existing merge semantics — this needs confirming against `mergeCorpus`'s actual merge-by-id behavior before committing to the design, but nothing in what was read suggests it assumes exactly one overlay.

**Build order:** This is the **largest, riskiest, most dependency-heavy fix in the milestone** — it touches the publish pipeline, the manifest contract, and the mobile fetch/cache/merge layer simultaneously, and a manifest-shape change is a wire-format break between old app binaries and new publishes. Sequencing:
- Land AFTER Fix 1 (so the publish pipeline isn't being restructured twice in flight) but does not need to wait for Fix 2 or Fix 4 — no shared files with either.
- Internally: (a) design and ship the new manifest shape with backward-compat parsing FIRST, published as a no-op (same single-snapshot content, new manifest shape) so old app binaries are proven to degrade safely before any split actually happens; (b) then split the publish pipeline's output; (c) then update the mobile fetch loop to consume the split. Each of (a)/(b)/(c) should be its own shippable, testable step — this is not a "do it all in one PR" change given the app's history with OTA-adjacent incidents (the v66 AsyncStorage incident, the dev/prod cache-overlay bug already documented in `CONCERNS.md`).
- Should almost certainly get its own dedicated research/spike before implementation, given the `mergeCorpus` multi-overlay question above is unresolved by this research pass.

**Blast radius if done wrong:** This is the fix most likely to reproduce the app's worst historical failure mode (users stuck on stale or broken content, discovered only on real devices). Specific risks: (a) a manifest-shape change that old cached app builds can't parse — must fail closed to "no update," verified by the existing `isManifest()` pattern, or old installs will think no update is available forever (silent staleness, exactly the `ealch-metro-caches-seed-json` / stale-bundle failure class already in project memory); (b) a partial-overlay bug in `mergeCorpus` when given multiple splits could produce a corpus that fails `validateCorpus` — already the pipeline's own hard gate, so this fails loudly at publish time, not silently on-device, which limits blast radius IF the publish-time gate is exercised with realistic split combinations before shipping; (c) a device that has level A1's split cached but not A2's, transitioning into A2 content, must degrade to "need network" gracefully — this is a new UI/UX state (partial content availability) that doesn't exist today and needs explicit handling in whatever screen shows "content not available offline."

## Fix 4 — Cold start (lazy-load seed.json)

**Current state:** `ealch-v2/src/services/content.ts:43`: `import seedJson from '@/content/seed.json';` — a static ES module import, evaluated at JS-bundle-parse time, before any component renders. `useContent`'s initial state is `corpus: SEED` (line 144), so the store itself assumes the seed is synchronously available the instant the module loads. `app/_layout.tsx` gates first paint on `contentHydrated` (from `useContent.hydrated`, set inside `initContent()`), and `initContent()` is called from a `useEffect` in `RootLayout` — so the *component* wait is already async, but the *module load* of the 4.66 MB / 2.42 MB-bytecode `seed.json` happens before `RootLayout` itself can even be defined, since it's a top-level import in a module `RootLayout` transitively imports.

**Concrete integration point:** `ealch-v2/src/services/content.ts` line 43 (`import seedJson from '@/content/seed.json'`) must become a dynamic `import('@/content/seed.json')` (or `require()` deferred inside a function) called from inside `initContent()`, not at module scope. This requires reworking:
- `const SEED = seedJson as unknown as Corpus;` (line 81) — currently a module-scope constant, needs to become something `initContent()` populates asynchronously.
- `export const useContent = create<ContentState>((set) => ({ ... corpus: SEED, ... }))` (line 139-147) — currently initializes with `SEED` synchronously at store-creation time (which is itself at module-load time, same problem one level up). This needs a real "not yet loaded" initial state (e.g., `corpus: null` or an empty-but-valid placeholder corpus) rather than assuming `SEED` exists synchronously, and every consumer of `useContent.getState().corpus` (the whole `content` accessor object at the bottom of the file, used throughout the app) needs to tolerate that briefly-empty state — today they implicitly cannot, because `hydrated` gates all of that access already via `app/_layout.tsx`'s `ready` check, which is good news: the gating mechanism this fix needs already exists, it just needs the seed import itself pulled inside it.
- `app/_layout.tsx` line 22 import of `useContent, initContent` from `@/services/content` — no change needed here; the `ready` gate already waits on `contentHydrated`, so once `initContent()` is genuinely async through-and-through, the existing gate does the right thing automatically.
- `app/splash.tsx` line 31: `setTimeout(() => router.replace('/home'), 2400)` — this is a **fixed 2400ms timer with no relationship to actual load state**. It should either (a) be removed in favor of navigating when `contentHydrated` (and other `ready` flags) actually become true, or (b) stay as a minimum-display-time floor but be combined with a real "did loading finish" check so a slow device doesn't navigate to `/home` before content is ready (currently this doesn't matter because `RootLayout`'s `ready` gate blocks rendering `Stack` entirely until hydrated — `splash.tsx`'s own timer racing `initContent()` is currently harmless because whatever route it lands on still sits behind the `ready` gate, but it does mean the 2400ms is dead weight once the seed load is fast).

**Data flow change:** `SEED` goes from "always present at any import time" to "present only after `initContent()`'s dynamic import resolves." Anything that imports `content.ts` and reads `SEED` or `useContent.getState().corpus` synchronously outside of the `ready`-gated render tree would break — this needs an audit (grep for `SEED` and `useContent.getState()` usage) before landing, to confirm nothing outside the React tree (e.g., a background task, a notification handler under Fix 5) reads content before hydration.

**Build order:** Independent of Fix 1/2/3. Should land AFTER Fix 3's design is settled if both are in the same milestone window, because Fix 3 changes `initContent()`'s shape substantially (per-split fetch loop) — doing the lazy-load rework first and then immediately restructuring the same function for splitting is wasted motion; doing them in the same phase, seed-lazy-load first within that phase, is fine. If Fix 3 is deferred to a later milestone, Fix 4 can land standalone at any time.

**Blast radius if done wrong:**
- *Low, if the existing `ready` gate is respected*: the app already has a working "don't render until hydrated" mechanism (`fontsLoaded && hydrated && progressHydrated && contentHydrated`) — this fix is really about moving WHEN the seed import happens (module-load vs. inside-the-gated-effect), not about building new gating. Get the dynamic import wrong (e.g., await it improperly, or leave a synchronous fallback path that still blocks) and the fix simply doesn't improve cold start — a measurable, low-severity failure (re-profile on device, try again).
- *Higher risk*: any code path that reads `useContent.getState().corpus` OUTSIDE the gated render tree (a background timer, a notification handler, a deep-link resolver that fires before `RootLayout` mounts) would previously get a valid seed-backed corpus and would now get `null`/empty and potentially crash or silently render nothing. This is exactly the kind of thing `useAlarmWatcher.ts`'s 15s interval (Fix 5's territory) or any future push-notification-tap deep-link handler (also Fix 5) needs to be checked against, since those are the most likely code to run outside the normal screen-mount lifecycle. **This is a concrete cross-fix dependency**: whoever builds Fix 5's notification-tap deep-link handler should be aware Fix 4 changes when content becomes available, and should route through the same `ready`/`contentHydrated` check rather than assuming content is always there.

## Fix 5 — Notification subsystem repair

**Current state (verified, matches `CONCERNS.md`):** `ealch-v2/src/services/notifications.ts` only exports `requestPermissions`, `scheduleDaily`, `cancelAll` — no `getExpoPushTokenAsync` call anywhere in the codebase (confirmed via full-repo grep, zero matches), no `addNotificationResponseReceivedListener` anywhere (same, zero matches). `useStore.ts`'s `notifs: {daily, report, nudge}` — only `daily` has any consumer (`setNotif`'s `if (k === 'daily')` branch at line ~226); `report`/`nudge` are persisted (`partialize` includes `notifs: s.notifs`, confirmed at line 356) but read by nothing. `app/_layout.tsx` already sets up `Notifications.setNotificationHandler` (foreground display behavior) and creates the Android notification channel (`practice-reminders`) — so the "notification shows up" half of the pipeline is real; what's missing is push-token registration, response handling, and toggle wiring beyond `daily`.

**Concrete integration points, by sub-piece:**

1. **Push token registration:** new code in `notifications.ts` — `Notifications.getExpoPushTokenAsync()` call, needs a place to store the resulting token. Given Fix 2's pattern (Adapty keyed to Supabase uid, mirrored to Postgres via webhook), the natural integration point is a new Postgres column/table (e.g., `profiles.push_token` or a dedicated table) written via a Supabase client call from the mobile app — this is genuinely new server surface, not an extension of anything that exists. Call site: alongside `enableDailyReminder()` in `useStore.ts` (the existing permission-request flow at line ~231), since token registration should happen at the same moment permission is granted.
2. **Notification tap → deep link:** `Notifications.addNotificationResponseReceivedListener` needs to be registered once, at app root — the natural home is `app/_layout.tsx`, alongside the existing `Notifications.setNotificationHandler`/`setNotificationChannelAsync` module-scope calls (lines 50-67) or as a new `useEffect`/custom hook analogous to `useForegroundSync()`/`useAlarmWatcher()`, both already mounted in `RootLayout`. The handler needs to call `router.replace(...)` or similar into whatever session the notification advertised — this is where the Fix 4 cross-dependency applies (must not fire before `ready`/`contentHydrated`, since resolving "the session that was notified about" likely needs the content corpus to resolve a lesson/anchor).
3. **Body template formatting:** `useStore.ts` line ~219: `STRINGS[get().lang].bannerText.replace('{t}', formatTime(alarmTime, clock24))` — only replaces `{t}`, never `{name}`. `PushBanner.tsx:31` does both replaces correctly. Fix: extract the double-replace into one shared function (e.g., in `i18n/strings.ts` or a small `formatBannerText()` helper) and call it from both `useStore.ts`'s `setAlarm`/`enableDailyReminder` and `PushBanner.tsx`, eliminating the duplicated, drifted logic. This is the smallest, lowest-risk piece of Fix 5 and has zero dependency on the other two.
4. **`report`/`nudge` toggles:** either wire them to real scheduled-notification variants (more `scheduleDaily`-like calls in `notifications.ts`, gated by their own toggle in `setNotif`'s branch), or — a legitimate, cheaper alternative — remove them from the UI until there's a real backend campaign to toggle, since `ealch-admin/src/lib/workers.ts` push-campaign send queue is explicitly a simulation today (per its own header comment) and wiring a client toggle to a server system that doesn't actually send anything would just move the "dead" problem from the toggle to the backend.

**Data flow change:** New: mobile → Postgres write path for push tokens (doesn't exist today in any form — `sync.ts` has no token-related code, confirmed by the same file read used for Fix 2). New: `Notifications.addNotificationResponseReceivedListener` → router navigation, a new event-driven entry point into the app that doesn't exist today (today the only entry points are `app/index.tsx` on cold launch and whatever deep link Expo Router itself resolves).

**Build order:** The four sub-pieces have different risk/dependency profiles and should NOT be treated as one atomic change:
- (3) Body template formatting: land anytime, independent of everything, essentially a bug fix.
- (1) Push token registration: can land independent of (2)/(4), but is low-value on its own without (2) actually using the token server-side for anything (no backend dispatch exists yet — `workers.ts` is simulated) — sequence this as "build the plumbing" but be explicit in the roadmap that it doesn't deliver user-visible value alone; it's a prerequisite for a future real push-campaign feature that `PROJECT.md`'s "Out of Scope" section explicitly defers ("Real push notification campaigns... not excluded, but a multi-day build the roadmapper may defer"). Given that, consider deferring (1) entirely unless the milestone's notification-repair goal is specifically "make the toggle honest," which doesn't require a token.
- (2) Tap → deep link: depends on Fix 4 being far enough along that "is content ready" is a stable, checkable condition before this handler resolves a session — sequence AFTER Fix 4, or at minimum coordinate the two if built concurrently.
- (4) report/nudge toggles: cheapest to resolve by REMOVING the dead toggles from settings UI (matches `notifs.daily`-only reality) rather than building the backend to back them, given `workers.ts`'s simulation status and the explicit out-of-scope note on push campaigns — flag this as a scope/product decision for the roadmap rather than pure engineering.

**Blast radius if done wrong:**
- *Tap handler wired before content is ready (Fix 4 interaction):* a notification tapped while the app is cold-launching could crash or navigate to a broken/empty screen if it doesn't wait for `ready`. Contained blast radius (one screen, recoverable by backgrounding/reopening) but a bad first impression for exactly the retention feature this fix exists to repair.
- *Push token registration without a consumer:* pure plumbing risk is low (a new column, a new write call, both additive), but forgetting the Adapty/Supabase-uid coupling pattern already established (Fix 2) — i.e., storing a token with no reliable user identity link — would produce tokens nobody can ever address, a similar "stranded state" failure to Fix 2's signed-out-purchase gap. Store the token keyed to the same `userId` used everywhere else.
- *Removing report/nudge toggles from UI:* purely a product/UX decision, effectively zero technical blast radius, but should be a conscious call-out to the user (Paul) rather than silently done, since it's a visible settings-screen change.

## Suggested Phase Ordering (for roadmap)

1. **Phase: Content-publish drift guard extension** (Fix 1) — isolated, fast, addresses the app's one actual data-loss incident's remaining exposure.
2. **Phase: Entitlement verification + signed-out-purchase fix** (Fix 2, sub-piece 1) — isolated, fast, mostly confirms existing Adapty behavior and closes one real gap.
3. **Phase: Notification body-format fix + toggle scope decision** (Fix 5, sub-pieces 3 + 4) — cheap, independent, can run in parallel with 1/2.
4. **Phase: Content snapshot split — design spike** (Fix 3, design-only) — resolve the manifest-backward-compat approach and `mergeCorpus` multi-overlay question before committing to implementation; this should probably be flagged in the roadmap as "needs phase-specific research" per the downstream ARCHITECTURE.md consumer contract.
5. **Phase: Content snapshot split — implementation** (Fix 3, build) — depends on 4's spike; touches publish pipeline + manifest + mobile fetch/cache layer together.
6. **Phase: Cold-start lazy-load** (Fix 4) — after Phase 5 if both are in this milestone (same function being restructured twice otherwise), or standalone if Phase 4/5 are deferred to a later milestone.
7. **Phase: Notification tap-handler + push token registration** (Fix 5, sub-pieces 1 + 2) — after Phase 6 (needs `ready`/`contentHydrated` to be a trustworthy gate for the deep-link resolution), and only if the roadmap decides push-token plumbing is worth building ahead of an actual campaign backend (see `PROJECT.md` Out of Scope note).

Phases 1-3 can run in parallel with each other (no shared files, no shared state). Phases 4-5 (snapshot split) are a dependency chain and the single largest risk concentration in this milestone. Phase 6 should not run concurrently with Phase 5 (same file, `content.ts`/`initContent()`). Phase 7's first sub-piece depends on Phase 6; its second sub-piece is best deferred given the explicit out-of-scope framing in `PROJECT.md`.
