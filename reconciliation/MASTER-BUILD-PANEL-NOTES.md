# Master Ealch Build - Expert Panel Notes

6-lens senior mobile-dev audit of the build draft. 71 findings. CRITICAL/HIGH were folded into the build; every finding is listed here for transparency (folded improvements are tagged inline in EALCH-MASTER-BUILD.md).

**Severity totals:** CRITICAL: 3  |  HIGH: 26  |  MED: 35  |  LOW: 7

---

## Architecture & Expo/RN — navigation, state, module boundaries, offline/sync, the CF-07 author-in-DB→snapshot pipeline, the CF-05 provider socket, and cross-phase sequencing, grounded in ealch-v2/ and ealch-admin/ code.

_Overall:_ The shipped foundation is genuinely strong and the draft is right to treat CF-07 as "harden and extend," not greenfield. The pure zero-runtime-import islands (schema.ts, content.logic.ts, progress.logic.ts) are real and node-testable; the three-layer content load (seed→cache→OTA) with four-gate sha256-verified snapshots is correct and the byte-parity between stableStringify in app and publish script is deliberately maintained; _layout gates first paint on all three persisted stores; the resilience contract (never block first paint, never throw, degrade to honest empty) is kept consistently. Phase 0 and Phase 1 sequencing ("amend the 17-item corpus before authoring") is sound and the SM-2 fold is clean and swappable. However, four load-bearing claims the draft treats as settled are contradicted by the code: (1) the CF-05 socket does NOT actually route on the console's model selection — the coach edge function discards the model the client already sends; (2) the "two byte-identical schema files" invariant is a misread — the admin file is a Drizzle DB schema, and the app schema is imported (single source), not duplicated; (3) per-user entitlement/server-sync has no identity substrate and no phase creates one; (4) the CF-04 client remote-audio path is entirely net-new, not "wired." These are concentrated in Phases 3, 4, 9 and the cross-cutting invariants, and each undercuts an acceptance criterion as written. The engine/schema phases (0,1,2,5) are largely solid; most findings below cluster in the integration and monetization phases.

- **[CRITICAL]** (Phase 3 — provider socket (CF-05), effort M) The draft asserts OPR routing→provider is 'true by construction,' but the wiring is broken at the last inch. The client already sends model: getConfig().models.general in the coach body (llm.ts:31), yet the coach edge function destructures only { messages, lang, promptVersion } (index.ts:187) and resolveProviders() (index.ts:112-166) selects a provider purely by which AI_API_*/OPENROUTER_*/NVIDIA_*/ANTHROPIC_* env secret is present, in a fixed priority order. The model field is received and thrown away; system_config is never read by the edge function. Flipping ai_routing in the console (→ system_config.config.models) therefore cannot change the live provider/model — only setting/unsetting a server secret and redeploying can.
  - Improvement: Make the edge function read `model` from the request body (or read system_config directly) and select the provider whose configured model id matches, instead of by env-var presence. Define an explicit model-id→provider registry (mirroring ai_models.provider). Only then is the Phase 3 acceptance criterion ('flip ai_routing → live provider changes, no rebuild') achievable. Add a resolver unit test that asserts a given model id routes to the intended provider and that the cost ceiling is enforced there.
- **[HIGH]** (Phase 1 / Cross-cutting invariant #1 — schema (CF-25), effort S) The through-line claim — 'the canonical shape lives in two files that must stay byte-identical, ealch-v2/src/content/schema.ts and ealch-admin/src/db/schema.ts; add a byte-diff CI check' — is factually wrong and misdirects the whole schema plan. ealch-admin/src/db/schema.ts is a Drizzle Postgres schema (pgTable + pgEnum definitions), not a copy of the TS content schema, and cannot be byte-identical to it. publish-content.ts imports the app schema directly (`from '../../ealch-v2/src/content/schema.ts'`, lines 32-41), so there is ONE canonical TS contract, imported, not duplicated. A file-level byte diff between a Drizzle file and a TS-types file is nonsensical.
  - Improvement: Reframe invariant #1: the app schema.ts is canonical and imported by the pipeline; the real, narrower drift risk is the Drizzle pgEnums (contentLevel, drillKind, itemKind, contentStatus) that manually mirror the app's `as const` unions. The CI check should compare those enum value-lists against the app unions, not diff files. Also note the cross-repo TS import couples the two checkouts (sibling paths, erasable-syntax constraint) — document it so nobody 'fixes' it by copying schema.ts into admin and creating the exact drift the design prevents.
- **[HIGH]** (Phase 9 — monetization (CF-14/15/23) + content 3.3.9 server attempts, effort L) Per-user entitlement and server-side attempts have no identity or sync substrate, and no phase creates one. Today useProgress is local AsyncStorage only, `premium` is a local persisted boolean (useStore.ts:208 upgrade()→premium:true; :296 persisted), and auth.ts deliberately holds no session unless Supabase is configured and the user actually signs in — nothing in the app gates on an authenticated identity. Phase 9's 'entitlement tied to a real per-user subscription synced to the admin subscriptions table,' the reconcile-on-foreground-against-RevenueCat customerInfo plan, and content 3.3.9's server `attempts` table all require (a) an established authenticated user id and (b) the app's first client→server write path — neither sequenced anywhere.
  - Improvement: Insert an explicit identity + sync-substrate phase before Phase 9 (and before any server attempts): sign-in gating, RevenueCat appUserID aliased to the Supabase auth uid, an offline entitlement cache that reconciles on foreground, and a defined conflict/merge policy for attempts if they ever sync. Keep `premium` as a derived read over the entitlement, but do not ship the entitlement→admin sync until the user identity it hangs off actually exists.
- **[HIGH]** (Phase 4 — Azure/Camille TTS (CF-04), effort L) The draft frames Phase 4 as mostly 'add azureNeural first in the edge chain,' but the client remote-audio path is entirely net-new. No client code invokes the tts edge function (grep: only coach, stt, and delete-account are invoked); tts.ts's `provider !== 'device'` branch is a comment-only no-op (lines 38-41) that always falls through to expo-speech. So even after Azure is added to the edge chain, nothing plays it until the client build exists.
  - Improvement: Scope Phase 4 as L/XL, not M. It requires: a client fetch→base64→expo-audio playback path; folding remote playback into tts.ts's once-only onDone/onError settle guarantee (lines 44-59); coordinating the new expo-audio player with stt.ts's pre-record stop, which today only calls Speech.stop() and would not stop a remote clip (audio-session contention); a remote-path timeout distinct from the Android 'not bound' device retry; and the content-addressed clip cache. Pre-synthesize lesson audio at publish time; live-synthesize only coach/roleplay.
- **[MED]** (Phase 1/2 — schema + pipeline (CF-13/24, CF-07), effort S) The publish item projection is a manual allowlist that silently drops new optional columns. publish-content.ts:109-138 hand-selects and hand-maps each item column; anything not listed never reaches the snapshot. Phase 1's new optional fields (register, cando, image_ref) will pass validateCorpus yet ship empty unless BOTH the SQL SELECT and the row map are updated — exactly the silent-omission class the pipeline exists to catch (required `modality` at least fails loudly, forcing the fix). Separately, `modality` as a pg enum array will hit the node-postgres enum-array parse bug the code already documents for `drills` (returns raw '{...}' string) and needs the same `::text[]` cast.
  - Improvement: In Phase 1/2, explicitly update the publish SELECT + mapper for every new column and add the `::text[]` cast for any new enum-array (modality). Better, add a publish-time assertion that every column present on content_items has a corresponding mapper key, so a future added column can't be silently omitted.
- **[MED]** (Phase 2 (systems) vs Section 2.3.1 (content) — DB content model, effort S) The two halves contradict each other on the content table layout. Shipped reality: lessons, units, and scenarios are all content_units rows discriminated by the contentKind enum with a jsonb `body` (admin schema.ts:205-234; publish reads `where kind='lesson'|'scenario'|'curriculum_unit'`). The systems half builds correctly on this. The content half (Section 2.3.1) instead proposes separate content_lessons and content_scenarios tables — a needless migration away from the working discriminated-union model and a direct contradiction the executing team must resolve before authoring.
  - Improvement: Standardize on the shipped content_units + kind + jsonb body model for documents; keep only content_items relational. Delete the content_lessons/content_scenarios proposal from the plan (or explicitly justify a migration, which is not warranted at 17 items with a working pipeline).
- **[MED]** (Cross-phase sequencing (both halves), effort M) Two un-reconciled phase plans cover the same work. Systems Phase 0-9 and Content P0-P7 both build the schema amendment, the modality SRS + sibling-gating + mastery, narration, the placement rebuild, and the generation pipeline, with different numbering and slightly different gating (e.g. placement is systems-Phase 6 vs content-P7; SRS is systems-5 vs content-P3). Executed by one team these overlap and risk double-building or divergent implementations of the SRS and schema.
  - Improvement: Before execution, merge the two into a single dependency DAG with one owner per workstream (schema, pipeline, SRS, narration, exam, monetization). The systems 'dependency spine' is the better skeleton; fold the content sections into it as the pedagogy/acceptance detail rather than a parallel numbering.
- **[MED]** (Phase 3 — provider socket / config plumbing (CF-05), effort S) config.models is a control-plane field the client barely consumes, which the draft overstates as existing wiring. models.content/audio/video are read into RemoteConfig (config.ts) but nothing on the client consumes them; the only consumer, models.general, is sent to coach and then discarded (see the CRITICAL finding). orchestrator is 'kie'|'nvidia' (draft catches the narrowness) but the deeper issue is there is no end-to-end path from any selected model id to any provider call.
  - Improvement: Phase 3 should specify the full socket contract — which config field drives which call site (coach general; tts audio; future content/video) — and wire each, rather than asserting 'the app already reads this.' Widen orchestrator to a free string keyed to ai_models.provider with nvidia default (default-merge in config.ts:48 protects old clients), and make audio routing actually select the tts provider once Phase 4's client path exists.
- **[LOW]** (Phase 1 — modality on the attempt log (CF-02), effort S) The modality field is a real persist migration, not the additive shallow-merge the store currently relies on. useProgress is deliberately still persist version 1 because added TOP-LEVEL fields survive via zustand shallow merge (comment at useProgress.ts:118-124). Making `modality` required on AttemptEntry breaks that assumption: persisted attempt ARRAY ELEMENTS have no modality and shallow merge won't rewrite them, so folding them through srsCards would produce undefined-keyed cards.
  - Improvement: Phase 1 must ship a genuine `migrate` (bump persist version to 2) that maps over the persisted attempts array (up to MAX_ATTEMPTS=20k) defaulting legacy entries to 'recognise' — this is the app's first non-trivial persist migration and should be called out and tested as such, not described as 'additive.' Sibling-gating then correctly treats those legacy attempts as recognise siblings.

## Content &amp; pedagogy

_Overall:_ This is a strong, unusually well-grounded content plan. It reads the shipped code honestly (the 17-item/all-A1 corpus, 3 lessons with empty itemIds, 14 empty units, SRS keyed on itemId only, SCHEDULABLE excluding speak/roleplay, the literal "1 → 3 → 7" srLadder, placement theatre) and its core diagnosis is correct: corpus volume and the dead lesson->corpus join are the real retention critical path, not any missing engine. The SRS design (modality split + sibling-gating + reps>=5/interval>=21 mastery + 20/day cap + Wilson weak-spots + composeSession) is the highest-leverage and best-specified part, and it faithfully implements CF-01/02/03/21. The schema-amendment-now sequencing (CF-25) and the additive-optional discipline are right. CF-11 (lift the A2 cap in UNIT_ID_RE/LESSON_ID_RE), CF-17 (id-first spine, delete the {title,sub} prototype arrays), CF-09 (pool from resume/weak-spots), the early-negation/can-do fixes, and the honest-copy fixes are all correctly targeted.

The weaknesses are (1) an ordering problem: the generation pipeline that produces the volume the whole plan waits on is scheduled last (P7) while the narration and examiner engines that only pay off at volume are built before it; (2) a uniform 15% human-review gate that under-reviews exactly the high-risk A2/B1 grammar; (3) two concrete integration gaps where narration-feeds-SRS collides with the activity-based SCHEDULABLE set; and (4) several shipped content-accuracy defects (the over-fine nasal contrast, the article-split unscrambler, missing IPA, the ungrounded examiner v1 prompt) that the plan's deterministic French gates will not catch and that its review policy does not explicitly assign to expert review. None are fatal; all are fixable within the existing phase structure.

- **[HIGH]** (Section 7 — Generation pipeline / build order, effort L) The plan names corpus volume 'the critical path the entire product waits on' and 'the throughput constraint,' yet the generation pipeline that produces volume at scale is scheduled at P7 — after the narration (P4) and examiner-schema (P6) engines that are only useful once volume exists. P1-P6 authoring is therefore hand-authoring 17->~760 items, and the 'prove-the-pipe-first' milestone is folded inside P7 rather than gating it. The dependency that actually threatens the timeline (pipeline + human-review throughput to reach a full A1 and a B2 bank) is de-risked last.
  - Improvement: Pull the prove-the-pipe milestone and a minimal generate->deterministic-gates->LLM-judge->Gate-H->publish loop forward to run in parallel from P2 (right after the lesson->corpus join lands), so authoring capacity ramps while the engines are built. Keep narration/examiner UIs late, but let the corpus they consume be filling the whole time. Make 'one A1 theme clears the full pipe on device' an explicit exit gate before any engine work, not a P7 sub-task.
- **[HIGH]** (Section 7.5 — Quality gates (Gate H), effort S) The publish contract applies a flat '>=15% of new items human-reviewed' gate to everything. But A2/B1 grammar (passe compose with etre, accord du participe, object-pronoun placement) is exactly where errors are subtle, systematic, and invisible to a learner who cannot self-correct — the same argument the plan uses to justify full review of Sons/A1. A uniform 15% sample lets wrong grammar through at the level where 'drilled wrong is retained wrong' bites hardest (PEDAGOGY note 70).
  - Improvement: Risk-tier Gate H: keep 15% spot-check for word-level themed vocab, but require 100% human review for grammar-bearing lessons (any lesson whose sections teach a tense/agreement/pronoun system) and for all Sons phonics content. Encode the tier as a machine rule keyed off lesson content type so the gate cannot be skipped by an author.
- **[HIGH]** (Section 5.3.4 + Section 3.3.1 — narration-feeds-SRS vs SCHEDULABLE, effort M) Section 5 makes narration 'produce'/'check' interactions write real AttemptEntry rows so the flagship Den lesson finally feeds the review queue — the single most important retention fix in that section. But srsCards() only schedules activities in the activity-based SCHEDULABLE set, which deliberately excludes speak/roleplay/lesson. A narration production attempt logged under a speak-type activity will be recorded and dropped by the scheduler, silently reproducing the exact 'retention-inert' outcome the section exists to fix. The same activity-vs-modality mismatch sits under the Section 3 modality refactor.
  - Improvement: Rework SCHEDULABLE from an activity allowlist to a predicate: schedule any attempt that carries a resolvable corpus itemId plus a modality, regardless of surface. Then narration produce/check and future speak drills schedule correctly, while open-response exam PO/PE (which have no atomic itemId) still route to the separate exam-skill surface as Section 4.3.3 intends. Add a progress.test.ts case proving a narration produce attempt becomes a due card.
- **[HIGH]** (Section 1 / Section 5 — shipped Sons content accuracy, effort M) The one shipped phonics lesson (sons.03.l1) teaches four distinct nasals including /oe~/ (un, parfum) as separate from /E~/ (in, vin), a contrast merged by most standard-French speakers, while the corpus has no unit at all for /y/-/u/ (tu/tout) — the contrast that actually causes misunderstanding (PEDAGOGY notes 92, 80). The plan's deterministic French gates (conjugator/gender-lexicon/espeak IPA) validate form but will pass a phonologically over-fine distinction as 'correct,' so this class of error is unguarded by the very pipeline meant to protect beginners.
  - Improvement: Add an expert-phonology review step to the Sons publish path (not just the LLM-judge): present /oe~/ as an optional traditional variant merging with /E~/, and author a /y/-/u/ minimal-pair unit as a priority. Fold this into the minimalPair discriminate-to-criterion step the plan already introduces, so perception precedes production for the contrasts that matter.
- **[MED]** (Section 6 — drills / Sentence Builder, effort S) sbWords splits 'un' and 'cafe' into two separate draggable bubbles, teaching beginners that the determiner is detachable from the noun — directly contradicting the 'gender travels with the noun / never a bare noun' principle that Voice Flash's vfItems correctly follows (PEDAGOGY note 88). Section 6 upgrades Sentence Builder to a rotating corpus selection but never fixes the article-split or adds a rule to prevent it.
  - Improvement: Treat article+noun as a single token for beginner sentence-building (one bubble: 'un cafe'), and add a validator/authoring rule that vocabulary items carry their article so gender stays part of the phonological word wherever the item is surfaced.
- **[MED]** (Section 3.3.3 — mastery as the Den progress signal, effort S) Section 3.3.3 swaps the Den's per-unit progress from itemsPracticed ('met') to isMastered ('retained'). Because isMastered requires interval>=21 days, an active daily learner will see 0/N on every unit for roughly the first three weeks — honest, but it deletes the early-progress signal at exactly the D1-D14 window the plan elsewhere treats as make-or-break, and it conflicts with the systems half (Phase 5) which says keep 'met' and 'mastered' as two distinct words.
  - Improvement: Show both counts on the unit (met M / mastered K / total N), or drive the progress bar with 'met' and reserve the mastered badge/check for the honest retention milestone. Do not let mastery-only be the sole visible unit signal in the first weeks.
- **[MED]** (Section 2 / Section 6 — IPA rigor, effort M) IPA stays optional (Item.ipa?), and the shipped cafe/objets/dictee items carry no IPA — only the wordOfDay literary entries do. For a product whose stated differentiator is 'sounding less foreign,' shipping the Sons track and pronunciation-context vocab without reliable IPA undercuts the core promise, and unreviewed LLM IPA risks teaching wrong phonemes a beginner internalises (PEDAGOGY note 71). The plan lists espeak-ng IPA as a publish gate but never makes IPA mandatory on the items that most need it.
  - Improvement: Make IPA a machine-gate (required) for all Sons items and for any item eligible for voiceflash or pronunciation drills, populated by a deterministic FR->IPA pass rather than the 15% LLM spot-check; route Sons IPA through full human review.
- **[MED]** (Section 4 — Examiner; shipped v1 marking, effort S) A shipped examiner v1 prompt already grades 'against CEFR rubrics' with no authored rubric, model answer, or examiner notes supplied — the precise ungrounded, memory-based marking the spec's own principle #1 identifies as the industry's quiet lie (PEDAGOGY note 22). Section 4 correctly requires rubric+targetItemIds for NEW ExamTasks but never says to retire or fence off the existing live scoring path, so the anti-pattern the section exists to prevent is already running.
  - Improvement: Explicitly re-scope examiner v1 to conversational roleplay only (unscored) and block any exam-scoring code path until rubric + model_answer + examiner_notes are present, matching Section 7's publish gates. Add this as a Phase-0-style honesty/store-risk fix rather than deferring it to the P6/P8 examiner build.
- **[MED]** (Section 3.3.2 — sibling-gating threshold, effort S) The stability floor that releases a produce/discriminate card (reps>=2 AND intervalDays>=7) is asserted but arbitrary and much weaker than the mastery bar. A recognise card at reps=2/interval=7 is only two clean passes in — far from stable — so produce siblings can still surface early and partially re-inflate the day-one volume that sibling-gating exists to cap. The 'caps day-one load' claim is stated, not validated.
  - Improvement: Justify the floor against the interval ladder (e.g. require the recognise card to have cleared the 3->interval*ease transition, not just reps=2), make it a named tested constant, and add a progress.test.ts assertion bounding the day-one produce-card count for a realistic first-session log.
- **[MED]** (Section 6.3.3 — Word of the Day level tie, effort S) Section 6.3.3 says Word of the Day will draw from 'the learner's active level+theme corpus' while simultaneously claiming the 'same-for-everyone / deterministic by day-of-year' property is preserved. These are contradictory: once the word depends on the learner's level, it is no longer the same word for everyone, which is the exact invariant wordOfDay.ts is built around and comments guarantee. Left unresolved this becomes a silent behavior change on the highest-traffic surface.
  - Improvement: Pick one contract explicitly: either keep it global (rotate a curated per-level pool but same word for all users at a given level+date) or drop the same-for-everyone claim. State which, and update the determinism note so the implementation does not inherit a false invariant.
- **[MED]** (Section 5.3.2 — narration pause timing, effort S) The narrated-lesson design keeps a fixed pause-per-level model (flat [pause:4]): 4 seconds of dead air after a one-word 'bonjour,' and possibly too little time to compose and speak an original line in the PRODUCE stage (PEDAGOGY note 16). Both dead air and rushed prompts erode the guided-lesson feel that is supposed to justify the premium Camille experience.
  - Improvement: Scale the interaction pause to the length of the segment being responded to (roughly word-count + a floor), keep the level default only as a minimum, and expose pause length as a user setting; pre-generated baked audio makes this cheap.
- **[MED]** (Section 4.3 — exam 'equated' claim, effort S) The exam model implies equated parallel forms with per-item difficulty rebalanced from real attempt data, but AttemptEntry records only score/verdict/correct on atomic items — no p-values, discrimination, or exam-item psychometrics — and a pre-launch app has zero sitting volume to equate against (PEDAGOGY note 24). 'Equated' is a psychometric claim the pipeline cannot substantiate at launch and is a CF-16-class trust risk if a fabricated band is shown.
  - Improvement: Launch with expert-judged difficulty and call forms 'parallel,' not 'equated'; label produced scores as practice estimates. If true equating is a goal, add item-analysis fields to the exam attempt schema now and hold the 'equated' language until enough sittings exist.
- **[MED]** (Section 1 / Section 7.3.1 — cross-level scaffolding, effort M) The volume table sets item/lesson counts per level, and 7.5 enforces >=30% recycled vocab and <=8 new items WITHIN a lesson, but there is no contract that a level recycles the previous level's constructions — leaving the A2->B1 difficulty cliff (PEDAGOGY note 13) unaddressed. Breadth is planned; vertical continuity between bands is not, which is what makes a leveled ladder actually feel earned rather than a step-function.
  - Improvement: Add a cross-level recycling gate to the publish contract (a B1 lesson must reuse a minimum share of A2 target items/structures) and specify the same-theme-at-multiple-levels pilot (cafe at a1/a2/b1) as the proof artifact for the ladder, as 1.3.5 gestures at but the pipeline does not enforce.
- **[LOW]** (Section 3.3.1 — modality assignment fidelity, effort M) The drill->modality map labels dictation as 'produce,' but dictation trains listening comprehension (CO) plus written production (PE), not spoken production; and it distinguishes flashcard fr->en (recognise) from en->fr (produce) even though the shipped flashcards drill does not currently capture or emit direction. If a drill emits the wrong modality, the modality split mis-schedules the very skill it is meant to isolate.
  - Improvement: Define modality per drill+direction explicitly and make each drill screen emit the correct value as part of AttemptInput; split dictation into its comprehension and production components or tag it honestly. Add a test that each drill's logged modality matches its retrieval direction.

## Data & schema (unified Schema v2 migration, migration ordering/reversibility, referential integrity, Supabase RLS, local persistence)

_Overall:_ The delivery-side data model is genuinely strong and the plan mostly sequences the right work: immutable text ids as the SRS key, a zero-runtime-import validator that enforces referential integrity at publish, a byte-parity checksum path (stableStringify + hand-rolled sha256 verified against node:crypto), the seed-as-floor merge, the fixed drills CHECK (0002), and the DB-as-version-counter are all sound and worth preserving. CF-25's "migrate now while the corpus is 17 items" is correct, and bundling CF-02/10/11/13/24 into one Schema v2 delta is the right call. The weaknesses are almost entirely in the seams the draft under-specifies: (1) the "two schema files stay identical" invariant is asserted but several concrete drifts already exist or are introduced by this plan (c2 enum, image_ref/imageRef naming, ExamTask.band typing) with no enforcing test; (2) there is no CI gate that validates the committed seed.json against schema.ts, so tightening validators can ship a silently-invalid bundled corpus that only breaks in the other repo; (3) the app's own control-plane supabase/schema.sql (profiles/review_items) is a divergent, uppercase-cased, FSRS-shaped second source of truth that the Systems half never reconciles, and there is no server persistence of the attempt log at all, so a reinstall wipes all mastery including for paying users; (4) migration reversibility, the publish query's explicit column list, mergeCorpus coverage of new Corpus arrays, and the "lesson-has-practice" gate ordering are all real steps the plan hand-waves. None are fatal; all are the kind of thing a seasoned team pins down before mass authoring begins.

- **[HIGH]** (Phase 1 (Schema v2) / Phase 8 (Exam), effort S) CF-10 removes c2 from the content LEVELS union, but the draft's own ExamTask type (Content Section 4.3.2) declares `band: Level` with a comment `b1..c2 (c2 scoring-only)`. After Phase 1, Level no longer contains c2, so ExamTask.band cannot hold the very scoring band CF-10 exists to preserve. This is a concrete type contradiction inside the draft, and the exam scoring surface (SCORE_BANDS result) is the whole point of keeping c2.
  - Improvement: Introduce `SCORE_BANDS = ['a1','a2','b1','b2','c1','c2']` as the authoritative scoring type and type ExamTask.band (and ExamSeries.passBand, rubric band, and any exam result) as SCORE_BANDS, not Level. Keep Level (content) at sons..c1. Add a validator test asserting a c2 ExamTask.band passes while a c2 Item.level fails.
- **[HIGH]** (Phase 1 (Schema v2) — cross-repo atomicity, effort S) The committed seed.json is never validated against schema.ts anywhere: content.ts casts `seedJson as Corpus` without validating, and schema.test.ts only exercises synthetic fixtures. So the moment Phase 1 tightens validateItem to require `skill`/`modality`, the bundled seed.json (17 items lacking those fields) becomes invalid, but the app repo's `node --test` stays green. The break only surfaces when ealch-admin re-runs publish-content, or silently at runtime as an invalid-but-cast corpus. schema.ts lives in ealch-v2; seed.json is regenerated by ealch-admin — the two must change atomically but nothing enforces it.
  - Improvement: Add a test in schema.test.ts that imports the real seed.json and asserts `validateCorpus(seed).length === 0`. That single test makes the app repo fail fast if schema.ts and the committed mirror diverge, converting the cross-repo hazard into a red CI light. Land it as part of Phase 1 acceptance, before tightening any validator.
- **[HIGH]** (Cross-cutting (control plane) / Phase 5 / Phase 9, effort L) The app's own Supabase control plane (ealch-v2/supabase/schema.sql) is never reconciled by the Systems half and carries three data liabilities: profiles.level defaults to uppercase 'B1' while the app's Level union is lowercase 'a1'..'c2' (any write from the app will store 'a1' against a 'B1'-defaulted, free-text column — a silent casing split); review_items is an FSRS-shaped, denormalized second SRS source keyed to nothing the client derives; and there is NO attempts/progress table, so the entire attempt log (the sole basis for SRS, mastery, weak spots) lives only in AsyncStorage. A reinstall or device change wipes all mastery — for paying users too — and Phase 9 syncs subscriptions but never the learning state it sells.
  - Improvement: Add a control-plane reconciliation to the plan (the Content half's 3.3.9 is right but the Systems spine omits it): make profiles.level a lowercase-constrained CHECK or enum matching Level and allow null 'unplaced' (drop the 'B1' default); replace review_items with an append-only `attempts(user_id,item_id,modality,verdict,correct,day,at)` mirroring AttemptEntry; add a foreground sync of the local attempt log so cards can be re-folded server-side and survive reinstall. Sequence the attempts table with Phase 1's modality field so both land once.
- **[HIGH]** (Phase 1 (Schema v2) — the two-file invariant, effort M) The plan leans on 'schema.ts and admin schema.ts stay identical' but names the new field inconsistently: the Systems half calls it `image_ref` (Item) while the Content half calls it `imageRef`. The app convention is camelCase fields (audioRef, itemIds) mapping to snake_case columns (audio_ref); getting this wrong desyncs the publish row-mapper, the validator, and voiceflash's resolver. The same class of drift already exists live: UNIT_ID_RE/LESSON_ID_RE are capped to (sons|a1|a2) while ITEM_ID_RE/SCENARIO_ID_RE already allow all six bands — proof the duplicated band lists drift in practice.
  - Improvement: Before authoring: pin canonical field names (camelCase app field imageRef <-> column image_ref) in one place, and derive the four id regexes from the const arrays (e.g. build the band alternation from LEVELS/TRACKS) instead of hardcoding the list in each RegExp, so CF-11's widening cannot miss one.   - Improvement: Extend validateCorpus in the same phase that adds each reference: resolve Lesson.scenarioId against the scenario set, ExamTask.targetItemIds against items, ExamSeries.taskIds against exam tasks, and Scenario.exam task references. Add duplicate-id checks for exam tasks/series to the existing dupes() pass. Cover each with a 'dangling ref is rejected' test mirroring the existing item/lesson tests.
- **[LOW]** (Phase 2 — publish atomicity, effort S) Snapshot version is computed in app code as prev+1, the content_snapshots row is inserted at step 9, and seed.json is written at step 10 AFTER the insert. A crash between insert and write leaves the DB recording a version whose committed git mirror never landed; and because the Storage upload happens before the row insert, a failed insert (or a race between two publishes computing the same prev+1) can orphan a snapshot object under a version the DB later reuses. Mostly fail-safe today but not documented.
  - Improvement: Either move the seed.json write before the snapshot-row insert (so the mirror can't lag the counter) or wrap version-selection + insert so a PK conflict is the single source of 'someone else published'; and add a cleanup/upsert note for orphaned Storage objects. Low priority given low publish concurrency, but worth a comment and a guard once more than one editor publishes.

## Monetization &amp; retention

_Overall:_ Phase 9 is the weakest-planned phase relative to its commercial weight, and Phase 0's fake-billing removal (CF-23) is the one genuinely solid part: removing `Visa ····4212` + the no-op Restore, extracting a reusable `pricing.ts`, and reinstating a real Restore in Phase 9 is the right sequence, with clean grep-based acceptance. Everything else in the monetization story has a structural hole the draft does not name: THERE IS NO PAYWALL. `premium` is read only in settings.tsx for display; nothing in the entire app tree gates on it, there is no coach cap, no level/theme lock, no offline gate. Phase 9 correctly plans the billing plumbing (entitlement, RevenueCat, restore, webhook sync) but plans none of the gates or trigger moments that actually convert, so it builds the ability to charge without building the thing that makes anyone pay. Compounding this, the approved IAP-first routing (CF-15) points in the opposite direction from the team's own unit-economics doc (web-first, ~$28/yr/sub lever, PPP-Africa as a named defensible wedge), and the whole of monetization is sequenced dead-last behind the exam engine and the full content build, needlessly gating subscription revenue on the $39 exam tier. The admin schema also cannot yet model the $39 exam SKU or Paystack. The D1/D7/D30 loop design in the content half is genuinely good, but it is pure content-volume dependent and has no revenue-retention layer (trial, dunning, winback, funnel instrumentation). Net: the plumbing is competently specced; the conversion system, the routing/margin strategy, and the sequencing are not.

## Performance & reliability (startup, list/render cost, audio/TTS, content-snapshot size, crash surfaces, low-end Android memory)

_Overall:_ The SHIPPED code has an unusually disciplined reliability contract and the draft preserves it well: first paint is gated on all three stores plus fonts and never flashes seed-then-merged (_layout.tsx:65-88); every service degrades to an honest offline/empty state and never throws (content.ts, config.ts, stt.ts, useProgress onRehydrateStorage); there is a module-scope error boundary + global handlers installed before first render (_layout.tsx:29-43); tts.ts guarantees onDone/onError fire exactly once across retries; drill screens clean up timers and stop TTS on unmount. None of that needs fixing. The real risk is uniform and structural: it is all invisible at today's 17 items and 833-line seed, and becomes the dominant cost at the planned launch corpus (Content S7.3.1 targets ~760+ items, ~130 narrated lessons, audio segment maps, exam tasks + rubrics — roughly a 40x data growth). Two patterns do not survive that scale unaddressed: (1) every content operation is synchronous whole-corpus work on the JS thread (a hand-rolled char-by-char SHA-256 + full re-serialize to verify a snapshot, plus a full referential re-validation of the cached corpus on every cold start), and (2) every SRS/home number is a fresh fold over the entire attempt log (bounded at 20,000), and Phase 5 multiplies the fold work (~3x cards via modality, plus sibling-gating, Wilson bounds, and composeSession) while every plan bullet reaffirms 'pure fold' and not one mentions memoization, incremental folding, off-thread hashing, or a memory ceiling. The plan is sound in intent; it needs an explicit performance budget attached to Phases 2, 5, and 7. Findings below are concrete and mostly small-to-medium effort.

- **[HIGH]** (Systems P2 / Content S2 — snapshot verification (content.logic.ts verifySnapshot/sha256Hex/stableStringify), effort L) verifySnapshot computes sha256Hex(stableStringify(parsed)) over the ENTIRE snapshot synchronously on the JS thread: a hand-rolled char-by-char SHA-256 (content.logic.ts:150-215) plus a full re-serialization that sorts every object's keys (stableStringify:135-144). At the current 20KB seed this is sub-millisecond; at the launch corpus Phase 2 explicitly grows (audio_assets manifest, per-lesson segment maps, narration bodies, exam rubrics — hundreds of KB to multiple MB) this is a multi-hundred-ms main-thread stall. It runs inside refreshFromRemote which is fire-and-forget so it does not block first paint, but it will jank whatever is interactive when an OTA lands (home animations, an in-progress drill). Phase 2 adds payload with no verification cost budget.
  - Improvement: Attach a perf budget to Phase 2: chunk the hash across frames (or run it after InteractionManager.runAfterInteractions), or move verification to a native crypto path / worklet. Also drop the redundant re-hash on the read path — the cache was already checksum-verified when written (see next finding), so re-verifying the cached copy every launch is pure waste. Benchmark verify time at the S7.3.1 target corpus and set a hard ceiling.
- **[HIGH]** (Systems P2 startup path (content.ts initContent → readCache → isValidCorpus), effort M) On every cold start, initContent (content.ts:81-89) awaits readCache, which JSON.parses the full cached snapshot and runs isValidCorpus = validateCorpus over the WHOLE corpus (schema.ts:554-637: per-item/lesson/unit/scenario validation + duplicate-id Sets + O(lessons×itemIds) and O(units×lessonIds) referential walks + a flatMap 'linked' Set). This sits on the paint-gating path — _layout gates first paint on contentHydrated (_layout.tsx:72-73), and setHydrated only fires after this completes. The cached corpus was ALREADY fully verified (checksum + validateCorpus) when it was written in refreshFromRemote, so this is a full redundant O(N) re-walk on the hot startup path, and Phase 2 adds more referential checks (imageRef, scenarioId, exam-task resolution) making it heavier exactly as the corpus grows.
  - Improvement: Trust the already-verified cache: store the manifest checksum alongside the cached snapshot and compare the (cheap) stored checksum instead of re-running validateCorpus, or skip structural re-validation entirely on read and only sanity-check shape. If any validation is kept, move it off the hydration gate (hydrate on the parsed cache, validate lazily after paint and roll back if it fails). Measure cold-start time-to-interactive on a low-end Android device at target corpus size.
- **[HIGH]** (Systems P5 / Content S3 — SRS engine (progress.logic.ts srsCards and all readers), effort M) Every SRS number is a full fold over the entire attempt log (bounded at MAX_ATTEMPTS=20,000, useProgress.ts:55). srsCards (progress.logic.ts:367-399) rebuilds a Map + per-item arrays + runs applyGrade over all attempts; dueCards, reviewDueCount, and upcomingCards EACH call srsCards independently (:403-426), so a single screen showing a count + an 'up next' preview folds the whole log twice. Phase 5 multiplies this: modality keying (up to ~3x the cards), a sibling-gating predicate that must cross-reference recognise siblings, Wilson lower-bound weak-spot ranking over a 30-day window, and a composeSession mixing pass — all derived on the fly from the raw log, with no shared memo, no incremental fold, and no windowing. The plan repeatedly reaffirms 'pure, node-testable fold' (good for tests) but never addresses that this is O(attempts) per derivation and there are now many derivations per render.
  - Improvement: Add a single source-of-truth fold: memoize one srsCards(attempts) result keyed on attempts identity and derive due/upcoming/weak/mastery/session from that ONE map, instead of each reader re-folding. Better, maintain the card map incrementally in the store — update only the touched item's card on each logAttempt — so reads are O(due) not O(log). Keep the pure functions for tests but cache their output. Set this as an explicit Phase 5 acceptance criterion with a benchmark at 20k attempts on low-end hardware.
- **[HIGH]** (Phase 0 / home.tsx render cost, effort S) Home computes reviewDueCount(attempts,today) (home.tsx:101, a full ~20k-entry SRS fold), streak(sessions,today,freeze) (:89, a loop of up to 3660 iterations with Set.has, progress.logic.ts:149), topWeaknesses, minutesToday, and wordOfDay directly in the render body with NO useMemo — while den.tsx, smartreview.tsx and review.tsx all correctly memoize their folds. Home is the most-visited screen and re-renders on every language toggle, browse-fold toggle (setField), and any attempts/sessions/errors change. So each home render re-does a 20k fold plus a 3660-iteration streak walk. On low-end Android this is a visible hitch on interaction.
  - Improvement: Wrap due/run/weaknesses/done in useMemo keyed on the specific store slices (attempts, sessions, errors). Trivial change, high payoff, and it aligns home with the memoization discipline the other screens already follow. Fold in with the Phase 5 shared-fold work so home reads the cached card map.
- **[HIGH]** (Systems P2 — OTA apply memory (content.ts refreshFromRemote), effort M) refreshFromRemote holds ~5 full-corpus representations live at once: the raw response text (:140), parsed object (verifySnapshot), the stableStringify string built for hashing, verified.corpus, JSON.stringify(verified.corpus) for the cache write (:150), and mergeCorpus(SEED, verified.corpus) allocating fresh arrays+Maps (:156, content.logic.ts:43-53). At the current 20KB corpus this is nothing; at a multi-MB launch corpus this is a transient 4-5x memory spike + heavy GC pressure during a background fetch, which on a low-end Android device is a realistic OOM / dropped-frames window. Not acknowledged anywhere in the plan.
  - Improvement: Reduce concurrent copies: reuse the already-parsed object for the cache write instead of the original text→parse→stableStringify→re-stringify chain; free text/parsed intermediates before merging; consider caching the raw verified text (not a re-serialized copy) so no second stringify is needed. Set a hard corpus-size ceiling and test OTA apply under an Android memory-pressure profile.
- **[MED]** (Phase 4 — Camille/remote TTS resolver + clip cache, effort M) The Phase 4 plan (fetch synthesized audio, play via expo-audio, cache by content-addressed key, fall back to expo-speech) omits three things a shipping team always needs: (a) no eviction policy for the on-device synthesized-clip cache — it grows unbounded on disk; (b) no mention of releasing/unloading expo-audio player instances — un-torn-down native players leak memory, and the Phase 7 karaoke segment player will create many; (c) the remote fetch has no specified hard timeout, so a slow synth can wedge a drill (the draft lists this as a 'risk' but leaves it a risk, not a requirement). The device path's exactly-once onDone/onError settle (tts.ts:44-59) must also be preserved across the remote→device fallback.
  - Improvement: Specify: an LRU/size-capped clip cache with eviction; explicit player teardown (release/remove) on unmount and on clip end; a per-request synth timeout that falls back to expo-speech; and a test that onDone/onError still fire exactly once across the remote→device fallback. Pre-synthesize lesson audio at publish time (batch) so only coach/roleplay synth is live, as the draft already suggests.
- **[MED]** (Phase 7 — narration karaoke highlight (segment startMs/endMs), effort M) The 7-stage player highlights the spoken segment via a startMs/endMs segment map. Implemented naively this means polling playback position at ~30-60Hz and re-rendering the narration text block each tick to move the highlight — on a low-end Android device, re-rendering a text/segment view 60x/sec is a classic karaoke jank source. The plan describes the feature and the schema but gives no rendering strategy or perf budget.
  - Improvement: Drive the highlight on the UI thread (react-native-reanimated is already a dependency) rather than through React state, or update at word-boundary granularity (advance only when position crosses the next segment's startMs) rather than every frame. Pre-index segments by time so lookup is O(1) per tick. Make 'no dropped frames during narration on a low-end device' a Phase 7 acceptance criterion.
- **[MED]** (Phase 4 / player.tsx — TTS completion watchdog, effort S) tts.speak has a retry watchdog for a speak that never STARTS (START_GRACE_MS, tts.ts:98-109) but none for a speak that starts and never reports DONE. Some Android TTS engines fail to fire onDone on long or edge-case utterances. In the player's auto-advance chain (player.tsx:98-122) onDone is the only thing that advances to the next line and eventually logs the session; if it never fires, playingRef stays true, the chain stalls silently, and logSession never runs. Same single-point dependence in review.tsx and any Phase 7 narration autoplay.
  - Improvement: Add a per-utterance max-duration timeout inside tts.speak that force-settles finishOk/finishFail (bounded by text length), mirroring the START_GRACE retry. This makes every autoplay/narration chain self-healing and guarantees the session log is written.
- **[MED]** (Phase 7 / Content S1 — Den unit-list render (den.tsx progressOf), effort S) den.tsx computes progressOf(u.id) per-unit inside .map on every render (den.tsx:47-52, 137-139). Each call runs content.lessonsOf(unitId) → lessonsOfUnit → getUnit (O(units) find) + indexById over ALL lessons (O(lessons) Map build, content.logic.ts:119-127) + a new Set from flatMap. So rendering the list is O(units × lessons) with fresh allocations, unmemoized. Content S1/Systems P1 expand the Den to 6 tabs and many more units and lessons, and the tab switch re-renders the list, so this scales as the worst case exactly when the corpus grows.
  - Improvement: Build a unit→itemIds index once with useMemo over the corpus (single pass, O(lessons)), and have each row look up its item set from that map instead of rebuilding an all-lessons index per unit. Combine with the memoized 'met' set already present.
- **[MED]** (Phase 1 — schema/drill-taxonomy migration vs cached snapshots (reliability), effort M) Phase 1 renames SKILLS→PracticeSkill and reworks the item taxonomy/DrillKind, and Content S3 changes SRS card keys. Existing installs carry a cached OTA snapshot written under the OLD shape. selectItems filters with it.drills.includes(drill) (content.logic.ts:78,84); if drill-kind strings change and the cached corpus predates the migration, decks silently return [] until a new OTA lands. flashcards.tsx then computes ProgressBar pct as (cardIx/deckLen)*100 = NaN when deckLen=0 (flashcards.tsx:151), the empty deck routes straight to the 0/0 'done' screen, and Den progress reads 0/N. The plan mentions two-file byte-parity CI but not runtime cache-compatibility across an app upgrade.
  - Improvement: Version the snapshot/DrillKind schema and invalidate (or migrate) an incompatible cached snapshot on app upgrade so a stale-shape cache can't produce empty decks; keep a back-compat mapping for old drill-kind strings during merge. Add a deckLen===0 guard so pct never becomes NaN. Make 'app upgrade over an old cached snapshot renders real decks' a Phase 1 acceptance criterion.
- **[MED]** (Content S7 — OTA cadence vs mid-session apply (reliability/jank), effort S) The D30 retention mechanism is frequent OTA content delivery. Today refreshFromRemote, on success, upgrades the LIVE corpus mid-session via useContent.setCorpus (content.ts:156), which triggers the synchronous verify (finding 1) and merge-allocation (finding 5) on the JS thread while the user is interacting. More frequent OTA = more frequent mid-session verify/merge spikes. The code already half-avoids this (results are 'seen next launch at the latest'), but the live upgrade path is on by default.
  - Improvement: Make the mid-session live upgrade opt-in / deferred: apply a downloaded snapshot at next cold start, or schedule the verify+merge behind InteractionManager.runAfterInteractions so it never lands during an animation or drill. This keeps the OTA cadence benefit without paying for it on the interaction path.
- **[LOW]** (Cross-cutting — bundled seed size + resident memory, effort S) seed.json is a static import (content.ts:19), so it is parsed into the JS bundle at startup and stays resident for the whole app lifetime, and mergeCorpus keeps both SEED and the merged corpus in memory (content.logic.ts:43-53). Harmless at the current 20KB subset, but the plan re-seeds and grows content; if the seed ever stops being a strict small subset it directly inflates startup parse time and steady-state memory on low-end devices.
  - Improvement: Keep the seed an explicitly bounded small subset (enough for a credible offline first-run only), document a size ceiling, and if it must grow consider lazy-requiring it. Add a CI check on seed.json byte size.

## Release & QA (EAS build/update, store rejection risk, test coverage, rollout sequencing of the greenfield rebuilds)

_Overall:_ The draft is strong on content-integrity plumbing and on the honesty/store-risk fixes that matter most for reaching review: Phase 0 correctly prioritizes CF-23 (fake billing/Restore) and Phase 6's 'ship an honest quick-check first' de-risks the Apple 2.3.1 fabricated-UI rejection on placement. The pure-island discipline (schema.ts, progress.logic.ts, content.logic.ts as node --test-loadable) is genuinely good for testability, and the content snapshot verify path (parse/checksum/invalid/version in verifySnapshot) is a solid delivery-integrity design. Account deletion already exists (auth.deleteAccount + delete-account.tsx + edge function), so the common Apple 5.1.1(v) rejection is already covered even though the draft never mentions it. Where the draft is weak is that it is a BUILD plan, not a RELEASE plan: it has a dependency spine (build order) but no release cadence for how 9 phases of JS/native code reach users. The repo has NO expo-updates/EAS Update (no runtimeVersion, no channels), so every phase is a full store binary + review cycle, and the plan repeatedly conflates the custom content-snapshot OTA channel (built) with code OTA (absent). eas.json is a skeleton, there is no CI anywhere, the risky integration surfaces have zero automated coverage while acceptance criteria lean entirely on node --test of pure functions, and the content OTA channel has no rollback/staged-rollout/kill-switch — the single highest-probability incident once LLM-generated French ships at volume. These are the gaps a seasoned release team would close before touching Phase 1.

- **[CRITICAL]** (Cross-cutting / Dependency spine, effort M) No EAS Update (expo-updates) is installed (absent from package.json; no runtimeVersion, no `updates` block in app.json, no `channel` in eas.json), yet the draft repeatedly claims the pipeline 'ships OTA without app-store review.' That is true ONLY for the custom content-snapshot fetch in content.ts. Every greenfield rebuild in Phases 4-9 (SRS engine, placement, Den narration player, exam engine, RevenueCat) is JS/native CODE that cannot ship through the content channel. The plan is a build order with no release plan: each phase implicitly requires a new store binary + review (multi-day), Phase 9's react-native-purchases forces a native rebuild regardless, there is no versioning/release-train strategy, no TestFlight/internal-track gating between phases, and bundling all 9 into one big-bang submission maximizes rejection blast radius.
  - Improvement: Decide the release model explicitly: add expo-updates with a runtimeVersion policy and per-profile channels so JS-only phases can ship as OTA JS updates between store builds, while native-module phases (4 audio, 9 purchases) are batched into planned store binaries. Define a release train (e.g. store binary at Phase 4 and Phase 9; OTA in between), stage each phase through an internal/TestFlight track before production, and stop describing code phases as OTA-deliverable.
- **[HIGH]** (Cross-cutting (tooling), effort M) There is no CI. `.github/workflows` and `.eas/workflows` are absent, so every quality gate the draft proposes is manual and optional in practice: the Phase 1 'two schema files byte-identical' drift check (explicitly called a classic drift trap), typecheck, the node --test suites, and `content:publish --dry-run`. For a build editing both the app plane and the ealch-admin plane in lockstep across 9 phases, an unenforced byte-parity invariant WILL drift and silently ship content the app cannot render.
  - Improvement: Land a CI workflow in Phase 0/1 (before the schema work) that runs on every PR: tsc --noEmit on both packages, node --test for the pure islands, the schema-enum diff across the two schema.ts files, and `content:publish --dry-run` as required status checks; gate merges on it. Enforce the invariant by machine, not by memory.
- **[HIGH]** (Cross-cutting (release config), effort M) eas.json is a skeleton that misconfigures or fails at release time. submit.production is `{}` — no ios.ascAppId/appleTeamId, no android.serviceAccountKeyPath/track, so `eas submit` cannot run non-interactively. No `channel` on any build profile (needed once EAS Update is added). No production env story: the app reads EXPO_PUBLIC_SUPABASE_URL / EXPO_PUBLIC_REVENUECAT_KEY at build time (env.ts), and with none set every service silently falls back to the offline/no-backend path — a production build with an unpopulated .env would ship with no backend, no OTA content, no purchases, and still pass a smoke test because nothing throws. The resilience design is great for uptime and dangerous for release verification.
  - Improvement: Fill submit.production for both stores; add channels per profile; wire production EXPO_PUBLIC_* via EAS secrets/eas.json env; and add a build-time assertion or post-build smoke check that FAILS the pipeline if a production build has empty Supabase/RevenueCat config, so 'accidentally shipped the offline demo' is impossible.
- **[HIGH]** (Phase 2 / Phase 7 (content pipeline & authoring at volume), effort M) The content OTA channel has no rollback, no staged rollout, and no kill switch. content.ts always fetches the single newest manifest.json and manifestIsNewer is strictly monotonic (version > current); the on-device cache only ever RAISES version. A snapshot that passes validateCorpus but is pedagogically wrong, has broken audio refs, or contains bad LLM French reaches 100% of users on next launch and cannot be pulled back — the only recourse is fix-forward with a higher version. No percentage rollout, no cohort channel, no remote freeze flag. Given Phase 7 generates hundreds of LLM-authored items, a bad publish is the highest-probability incident in the plan with zero mitigation.
  - Improvement: Add release-safety to the delivery plane before scaling generation: a staged rollout (manifest carries a rollout % or the app hashes device id to gate adoption), a remote kill/pin flag the app honors to freeze on the cached version, and a documented rollback runbook. Since the counter is DB-derived (prev+1) and content_snapshots already exists, track which version each cohort holds so a bad version can be pinned out.
- **[HIGH]** (Cross-cutting (QA), effort L) Test coverage is confined to the pure islands (schema, content.logic, progress, score, time, i18n via node --test). The highest-risk NEW surfaces have no automated coverage and the draft proposes no harness for them: the RevenueCat webhook->admin subscriptions sync + foreground reconciliation (Phase 9, which the draft itself flags as integrity-critical), the TTS remote->device fallback settle-once guarantee (Phase 4), the on-device OTA download->verify->cache->merge round-trip (Phase 2), the useProgress persist-version migration (Phase 1/5), and the narration player pause-at-interaction + logAttempt wiring (Phase 7). No device/e2e tooling (Detox/Maestro) exists. Acceptance criteria that say 'node --test green' never touch these.
  - Improvement: For each stateful/integration phase require a test type matched to the risk, not just a pure-function test: contract/mock tests for RevenueCat sync and reconciliation, a JS round-trip test for verifySnapshot against a real publish output (byte-parity asserted), a versioned-store migration test for useProgress, and at least a Maestro/Detox smoke flow (launch -> placement -> drill -> review) run in CI on one device profile before each store binary. Add these as explicit acceptance criteria.
- **[HIGH]** (Phase 9 (monetization), effort M) Phase 9 is scheduled last with no allowance for IAP lead-time or first-submission scrutiny. RevenueCat + App Store Connect needs the paid-apps agreement, banking/tax forms, product creation, and — critically — the IAP products (Premiere subscription AND the $39 exam tier) must be submitted for review WITH the first binary that references them; Apple reviews IAP alongside the app and 3.1.1/3.1.2 scrutiny is heaviest on a first paid submission. react-native-purchases is a native module, so Phase 9 also forces a native rebuild and can never be a JS-only OTA update. None of this timing is in the plan, and it gates launch revenue.
  - Improvement: Pull commercial setup (agreements, banking, product IDs in both stores, RevenueCat offerings) forward to run in parallel from Phase 0, not at Phase 9. Budget an extra review round for the first IAP submission. Ship a real sandbox purchase + restore + reconciliation through TestFlight/internal track before production, and confirm via automated entitlement test that the $39 tier grants ONLY exam access.
- **[MED]** (Phase 1 / Phase 5 (persist migration), effort M) Phase 1 bumps the useProgress persist version with a migrate defaulting legacy attempts to modality 'recognise', and Phase 5 relies on it. This is a data-integrity event: if migrate throws, onRehydrateStorage degrades to 'no progress', silently wiping history. The draft neither tests migrate against old/corrupt shapes nor addresses forward/backward compatibility — if a v2 store binary is rolled back to a v1 binary (a normal release safety move), the already-migrated v2 attempt log is unreadable by v1. Low blast radius pre-launch, but irreversible once real users accumulate history, which is exactly why the draft lands modality early.
  - Improvement: Ship migrate with a versioned-store test suite (old->migrated, corrupt->clean empty, idempotent re-run) and make the on-disk format forward-tolerant (v1 binaries ignore unknown fields rather than failing) so a store rollback cannot brick returning users. Add 'migration reversible or forward-tolerant' to phase acceptance criteria.
- **[MED]** (Cross-cutting (native config), effort S) expo-speech-recognition is pinned to ^56.0.1 while the entire Expo SDK and every other native dep is ~57. A config-plugin native module a full major version behind the SDK is a classic EAS build break or a runtime crash on the new architecture (RN 0.86 / reanimated 4). This is the STT module the placement rebuild, exam PO/PE capture, and narration produce/check interactions all depend on — a build failure here blocks every downstream phase.
  - Improvement: Align/pin expo-speech-recognition to the SDK-57-compatible release and run a real `eas build` (dev + production profile) early, before Phase 1, to prove the native toolchain compiles. Pin exact versions on all native modules for reproducible release builds.
- **[MED]** (Phase 5 / Phase 7 (retention-loop delivery), effort S) The D1 return hook (daily reminder / composeSession) is the content half's core retention mechanism, but the notification delivery path has release gaps. app.json android permissions do not list POST_NOTIFICATIONS (Android 13+ runtime permission for local notifications); expo-notifications' plugin usually injects it, but there is no explicit runtime request tied to enabling the daily reminder beyond the settings toggle, so on Android 13+ the reminder can silently no-op. Separately, Play Console requires a foreground-service USE-CASE declaration form at submit for the declared FOREGROUND_SERVICE_MEDIA_PLAYBACK permission — a missing form blocks the release.
  - Improvement: Explicitly declare POST_NOTIFICATIONS and wire a runtime permission request at reminder-enable time, with a QA check on an Android 13+ device that a scheduled reminder actually fires. Complete the Play foreground-service declaration as a named release-checklist item. Add 'daily reminder fires on Android 13+/iOS' to the retention-phase acceptance criteria.
- **[MED]** (Phase 8 (exam) — store-listing risk, effort S) The draft handles in-APP exam copyright well (examDisclaimer, format_version, original-items-only, Gate H) but misses the distinct STORE-LISTING risk: putting registered marks 'TEF Canada / TCF Canada / DELF B2' (marks of France Education international and CCI Paris) in the App Store/Play listing, screenshots, keywords, and prominent UI can be rejected as implying affiliation independent of in-app content, and is trademark exposure. CF-22 only fixes the chip label, not listing metadata.
  - Improvement: Add a release-listing review step: use descriptive 'prep for…' phrasing with a visible non-affiliation statement in the listing and first-run UI, clear it with legal before submission, and keep the marks out of ASO keywords/screenshots. Treat it as a store-review gate, not just an in-content one.
- **[LOW]** (Cross-cutting (project identity), effort S) Project identity is inconsistent and bites at submit time: app.json slug 'wonerock', owner 'wonerocks-team', product name 'Ealch', bundle app.ealch.mobile, scheme 'ealch'. Mismatched slug/owner vs brand complicates eas submit, store listing, and analytics attribution. The 'ealch' deep-link scheme is also the vehicle for the Phase 7 OPR 'open a draft on device' preview (orphan 14), which needs associated-domains/intent-filter registration that isn't configured.
  - Improvement: Reconcile slug/owner to the brand before the first production build (or consciously record why they differ), and configure associated domains / Android app links if the OPR live-preview deep link is in scope, so QA can actually open drafts on device.
